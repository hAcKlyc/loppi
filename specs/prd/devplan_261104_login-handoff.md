# 登录启动交接与设置刷新稳定性

开启登录启动时，已有普通 Core 必须完成一次退出并由登录 Core 接管，不能被 GUI/CLI 的按需启动反复抢占。设置读取失败后保留已有值和错误，直到该资源真正读取成功；不隐藏真实失败。不改变录制意图、系统登录项注册方式或升级协议。

## 执行台账
### 开发契约
- 必赢场景：普通后台运行且持续有查询时，登录后台有界接管；重复登录启动不替换已有登录 owner；关闭登录项后的普通启动仍可用。
- 原子交付：Core 启动竞争修复、设置刷新稳定性及回归验证一起交付。既有 YieldToLogin 协议不变。
- 必须保证：唯一数据库 owner、交接前完成采集退出、读取失败不伪造配置成功、相互独立的设置读取分别清除自己的错误。
- 明确不做：修改系统登录项实现、自动重试业务写请求、迁移数据库、发布或覆盖日常安装。
- 本次负责的问题：登录/普通启动饥饿循环，刷新预清空错误导致的跳动。
- 状态来源：Core 的 core.lock 是唯一运行 owner；SMAppService 是登录项事实源；React 仅保存最近快照和请求结果。
- 复用抽象：acquire_owner_lock/acquire_lock、platform::try_lock_exclusive、YieldToLogin、refreshContext、LoadBoundary。
- 同步调整：在既有 Core 启动入口增加短期启动互斥文件 core-start.lock；登录接管期间持有，普通启动直接让位。它只串行化启动，不是业务状态或第二个运行 owner；失败/进程退出自动释放。
- 不变量：Core 唯一写库；按需查询不自动开麦；不使用父 GUI 已持有的 lifecycle.lock，避免父子等待死锁。
### 验收与结束条件
- 真实隔离进程验证：普通 owner + 连续查询/按需竞争 → 登录 owner 接管并稳定；重复登录启动退出；退出后普通 Core 可再次启动。
- 前端验证：首次失败、持续失败及恢复期间，错误只在成功后清除；已有设置控件保持挂载。
- 静态、相关回归、构建、三路 cross-review 全通过；任何未覆盖的平台如实记录。
- 影响映射：Core 修改重跑 Rust 检查及进程回归；App 修改重跑前端静态与 UI 回归。
