# 讨论台账：离线模型作为客户端必需资源及跨平台构建发行

> 已收敛并实施为 0.1.8：Core 只读随包资源、默认 Universal2，Windows 单独做。用户要求跳过额外流程，本轮不做 CI、完整重评测或独立多轮审查。最新实现见[打包说明](../../tech_docs/offline-macos-packaging.md)。

## 岔路清单

- [x] 交付体验 → 本地识别必需模型随安装包交付，安装后无需额外下载才能使用本地粗转。
- [x] 模型运行时位置 → Core 随包只读加载，不复制。
- [x] 平台范围 → 本次macOS arm64/x86_64；Windows适配独立需求，当前不设计或实现Windows客户端。
- [x] Mac发行矩阵 → 默认 Universal2，保留显式单架构构建。
- [x] 发行契约 → 必要本机验证、签名公证及 DMG；原生 Intel/最低系统验收未执行。
- [x] 模型升级策略 → 固定随 App 版本，无独立更新器。

## 决策台账

### D1：核心模型是软件交付内容

- 定了什么：设计以完整离线安装包为默认目标，X-ASR/VAD及声纹对应模型随App交付；首次模型就绪不依赖Hugging Face/GitHub网络。
- 为什么：目前下载前无法走通核心本地识别流程，安装包与必需资源分开下载增加首次使用门槛。
- 用户原话：「主要是我理解这个资源相当于这个软件必须依赖的资源对吧，这是你核心功能组件。下载完之前都用不了。。」

### D2：先形成可评估的架构和构建方案

- 定了什么：当前任务是设计、核实技术前提与记录方案，不直接改运行逻辑或打新包。
- 为什么：资源位置、生命周期、跨平台边界与发布矩阵影响长期架构，需先把取舍讲清。
- 用户原话：「设计一下，正确架构这玩意该怎么搞？以及考虑到 mac intel arm 还有 windows ，不同平台的打包。build 的脚本也得好好仔细设计一下。」

### D3：本次平台范围仅macOS

- 定了什么：本次设计覆盖Apple Silicon和Intel Mac，Windows客户端适配单独做。资源清单与构建目标避免写死宿主架构，但不引入未使用的Windows平台层或发布脚本。
- 为什么：Windows客户端不是仅换打包格式，需要独立的平台适配；当前先把Mac核心体验和发行链路设计完整。
- 用户原话：「哦。那 windows 先不做。先把 mac 做完设计好，之后我在单独做 windows 的适配」

## 张力时刻

- 只把模型附在DMG旁边不会随拖拽App一起安装；现有Core也只识别用户数据目录的已安装包，不能仅改变DMG内容。
- 跨平台权重可能相同，原生引擎、二进制和平台集成不同；“Tauri支持Windows”不代表当前hear源码已支持Windows。
- 之前提出首次复制约205MB模型到数据目录，需要重新核实是否会制造重复副本、双重事实源和升级清理复杂度，不能先将复制当作既定设计。

## 必赢场景

用户在支持平台下载安装包，将应用正常安装，断网、空用户数据目录下首次启动，本地模型校验和真实推理均可就绪，不需要额外模型下载；同一版本所有组件/原生库/模型身份可追溯。升级不改历史结果归属，不破坏正在运行的Core/worker。

## 原子交付边界

- 当前交付：架构设计讨论稿、源码与官方资料核验、推荐方案/取舍及明确待定范围。
- 后续开发范围待用户确认：资源所有权/路径、模型清单、各平台构建与验证、旧包升级及默认UI行为必须作为完整契约收敛，不能把半成品跨平台支持作为完成。
- 不在本次直接执行：生产代码变更、安装/重启现有客户端、远端发布、重跑ASR排行榜。

## 技术前提

- 已核实：现0.1.7来自干净提交4d2c5eb；资源共204630545字节，模型单独UDZO实测163855288字节，完整离线DMG估算约180–190MB（尚未做含模型的release）。
- 已核实：model_pack.rs持有固定SHA/来源、用户目录安装/暂存；Core持有ModelState/PrepareModels与资源调度，worker只接受路径并计算。现有build_release.sh→build_macos.sh→package_macos.sh，只构建宿主架构并执行签名/公证。
- 已核实：Apple/Tauri支持Universal；四个Mach-O都需双slice。官方2.0.0存在arm64、x64和Universal2静态库，Universal2包API digest为8ed41bf3b27ce55d6527bbc0f7754598c5afbb18e814ff0bddbc9ecd50fb09c5，尚未下载逐成员核验。
- 已核实：Core从自身路径找同目录worker，CLI/GUI已定位同一个登录项helper；将模型放helper自己的Resources可使三入口共用定位，无需GUI设置资源路径。现有Core启动线程与加载检查可复用。
- 已核实：当前最低系统13.0，较新SDK用于编译；系统声有旧ScreenCaptureKit及动态解析较新Tap路径。不能由新SDK版本直接推定最低运行系统。
- 已核实：当前首启完成还要求两项云服务及权限，完整模型离线就绪不代表云端事件整理/精转离线可用。
- 已核实：资源须在签名前定稿，覆盖App应先完整退出Core/worker；既有GUI启动交接不保证任意运行中覆盖安全。GitHub当前有独立arm64/Intel runner标签，现有单job不覆盖两者。
- 实现时必须验证：所用native库的实际双slice/最低OS/CPU要求，两个平台的Core/worker离线真实运行与模型资源表现，最低系统/升级验收；如换Universal原生包，ARM旧输入也受到影响，须重跑受影响X-ASR配置，不重跑其它候选排名。
- 对决策的影响：推荐Core bundle只读资源与单一Universal2发行，采用明确target的构建编排和最终包验收；未实测平台不宣称支持。

## 当前推荐方案（待确认）

完整设计：[必需离线模型与Mac构建发行](../../research/2026-10-25-offline-assets-macos-build-design.md)。资源位置、Universal默认发行及随App固定模型升级是本轮提出的建议，尚未视为用户已批准生产改动。Windows排除是用户已明确的范围。

构建由一个Node入口编排现有Mac工具，先校验固定资产和目标，再完成两套编译/合并、整包验证、由内到外签名、DMG/公证/装订和实际挂载。正式release必须绑定干净Git提交、两slice四组件、模型/native锁身份和最终checksum。原生Intel/ARM验收均为完成门槛，不能只看交叉编译。

本轮已形成可评估设计稿，未实现脚本/生产代码，也未打包新的离线release。后续需确认核心推荐并在实施PRD中定量化模型回归与最低系统准入条件；当前不是ready-for-development文档。
