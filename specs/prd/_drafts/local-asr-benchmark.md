# 讨论台账：真实事件音频的本地 ASR 基准评测

## 岔路清单
- [x] 数据来源与规模 → 从历史真实事件中抽取约 10 组，保留音频与答案，长度可不同。
- [x] 评估对象 → 当前本地粗转录模型及经过调研筛选的其他本地 ASR 候选。
- [x] 优先覆盖的真实使用场景与语言、声音条件的权重 → 按历史使用分布选样，兼顾难例；具体配额依据候选池统计拟定。
- [x] 参考答案的可靠性要求，以及疑难音频的最终校对方式 → 校对全部由 Agent 承担，不安排用户听校；保留核验依据与不确定区间，不能冒称未经实施的人工听校。
- [ ] 目标设备范围，以及准确率、速度、内存、体积、能耗的取舍标准。
- [ ] 交付边界：研究评测资产与报告、可重复执行的工具、是否包含产品模型替换。

## 决策台账
### D1：基于真实历史事件构建小型固定测试集
- 定了什么：约 10 组真实事件，保留可复测音频与答案；从现有精转录出发校对参考答案。
- 为什么：评价实际场景中的粗转录质量，需要有可追溯、可重复使用的真实数据；现有精转录只是参考，不能未经验证视为正确答案。
- 用户原话：「数据来源：从之前的日志中找出一批数据。」「数据规模：不需要很多，大概 10 组事件即可，每组事件的长短可以不一。」「利用现有的精转录效果作为参考，甚至你可以想办法对正确答案做一些矫正，确保整体结果是准确的。」

### D2：实际测量模型效果与资源成本
- 定了什么：建立当前模型基线，对候选本地模型实际跑分，比较效果、内存、安装体积、能耗等。
- 为什么：为后续优化与升级提供场景相关的依据；模型官方榜单不能替代同一音频、同一设备上的实测。
- 用户原话：「粗转录的质量是非常重要的一件事。」「测试不同模型在我们的测试集里跑分的情况，并对比它们的内存占用、安装包大小等相关指标。」「最终希望得到本地模型在效果、能耗等方面的综合评估结果，作为后续我们优化体验、升级模型准确率的参考。」

### D3：选样按历史使用分布，兼顾难例
- 定了什么：以真实日常使用的场景分布为主，补少量困难片段。按独立活动分组，同一活动的切片仍属于同一组；先选样、冻结，再运行候选，不按候选得分反向挑样。
- 为什么：让评测反映日常体验，同时保留发现薄弱环节的能力；防止同一长活动的相关片段挤占约 10 组的覆盖面。
- 用户原话：「按历史使用分布选样，兼顾难例（推荐）」

### D4：参考答案由 Agent 负责核验与修订
- 定了什么：用户不参与矫正；由 Agent 建立可追溯的参考答案，利用原声、现有精转与独立识别交叉核验。无法确认的内容显式标注并按冻结规则单列；不能将自动共识声称为人工金标准，或为了消除分歧凭语境补字。
- 为什么：用户明确将整项工作交给 Agent；避免把最耗时的标注任务推回用户，同时诚实呈现答案的证据强度。
- 用户原话：「我不去做矫正，这会都是你的，你自己想办法」

### D5：候选必须经过广泛、近期、以 CPU 可部署性为约束的调研
- 定了什么：查询 Hugging Face、GitHub、社媒及其他渠道，主动查找近期模型与推理运行时进展；社媒用于发现线索，技术结论回到作者资料和代码核验。首要约束是本地 CPU 可覆盖，不能用 GPU 高并发榜单代替。
- 为什么：最初候选只是初筛，用户担心遗漏近期更好的方案；模型权重与量化/推理运行时共同决定 CPU 上的实际可用性。
- 用户原话：「关于模型的部分，我觉得你先别拍脑袋。我希望你去网上使劲搜一搜，因为我感觉最近一段时间可能有不少新的进展。」「你可以去看看 Hugging Face、GitHub 还有社媒等各个渠道」「但都应该是当前的这个资源水平--本地 CPU 就能 cover 住等等」

## 张力时刻
- 用户要求不要凭已有候选拍板，要广搜近期进展；需把“知道某模型”和“查证当前 CPU 部署可用性”明确区分。
- 用户明确拒绝参与矫正，将参考答案工作全部交给 Agent；不能继续把听校任务作为用户门槛。
- 需要区分精转录参考与经过音频核对的正确答案；需要区分模型本身的错误与录音、VAD、切分造成的错误。

## 技术前提
- 已核实：当前代码使用 sherpa-onnx 1.13.8，粗转录为 SenseVoice INT8，模型路径 `models/speech-v1/sensevoice/model.int8.onnx`；依据 `crates/hear-worker/src/main.rs`、`crates/hear-core/src/model_pack.rs`、`crates/hear-core/src/coarse.rs`。
- 已核实：生产粗转配置为 `language=auto`、`use_itn=true`、2 线程；16 kHz 输入，持续语音约 20 秒主动切分，输入硬上限 30 秒。基线应复用生产解码、逐块重采样与分段，不能简单将整场音频交给模型后声称复现当前链路。
- 已核实：私有数据位于 `~/Library/Application Support/hear/`，SQLite 与 Opus 文件是正文/音频依据，日志用于追溯；只读初查约 484 个未删除事件、23,158 条粗转、31,599 条精转（运行中会变化），425 个事件在时间上同时与三类数据相交。该数字只是候选池，不代表已完成音频完整性或当前精转归属验证；最近 100 个留存媒体引用均存在。
- 已核实：参考精转来自火山录音文件识别，当前请求资源 `volc.seedasr.auc`，当前 `submit_audio` 只发送音频及识别/说话人选项，不发送粗转文本。用户纠错存于 `text_corrections`，初查只有 2 条，不能假定现有精转普遍经过人工校对。当前有效结果须结合 `event_asr_refs`、`cloud_tasks`、`precise_segments` 与人工纠错读取，不能按时间相交拼入旧版本或重复请求。
- 已核实：本机 Apple M5、24 GiB 统一内存、macOS 26.6.2；这是可用实验设备，尚未确认它是否代表目标最低设备。
- 已核实：仓库已有 `scripts/macos_rusage.c` 与资源采样/报告工具，可提供进程物理内存足迹、CPU 时间、进程能耗计数；现有文档明确能耗计数只用于同机趋势，不能等同整机电池续航。GPU/系统代管模型须额外核查计量覆盖，不能仅以 worker RSS 比较。
- 已核实：广泛调研与公开模型/运行时元数据已记录于 [CPU ASR 调研报告](../../research/2026-10-24-local-cpu-asr-survey/REPORT.md)。新增 FireRedASR2 CTC、X-ASR、MOSS 0.9B、VibeVoice-ASR-BitNet、Cohere 等值得实测的路线；Qwen 已有专用 CPU 实现。31 次模型精确查询和 10 个仓库提交记录已留存；尚无候选的本机分数、内存或能耗实测。
- 已核实：本机已安装的 sherpa-onnx 1.13.8 Rust 源码包含 FireRed CTC、Fun-ASR-Nano、Dolphin、Omnilingual CTC 配置；这只确认 API 类型存在，不等于所有新版权重已实际适配通过。
- 待核实：10 组样本的完整媒体、真实声音条件及有效精转覆盖；候选在 Apple Silicon 上的实际部署、量化与运行时选型；精确能耗测量路径与测试条件。CPU 是主评测约束，Metal/MLX GPU/ANE 仅可单列补充；先按现有 2 线程预算比较。
- 对决策的影响：冻结音频时应能追溯原事件与输入分段；评测要避免参考答案偏差，并覆盖实际部署条件。

## 待讨论的方法建议（未当作用户已确认）
- 选样先按历史场景分层，兼顾常见场景与难例，在跑候选前冻结。不要只挑当前模型已知失败片段；十组是本用户场景的回归集，不代表普遍 ASR 排名。
- 每组保留各原始音源、可复现的测试音频、有效精转初稿、校对答案、可评分/听不清区间与来源/时间/文件指纹清单；不把双路重复拾音拼成一条参考答案。
- 参考答案逐字忠于原声，保留口误、重复、自我纠正，不润色改写。独立识别可协助发现疑点，但多模型一致不等于正确；听不清内容标记，不凭语境补写。用户已明确全部校对由 Agent 负责，不安排用户听校；参考答案中不确定区间与受评模型参与核验的来源必须记录。
- 同一固定分段比较模型识别能力，并另测实际粗转链路覆盖、重复、漏字与失败。已有原声被清理/丢弃而不能听证的缺口不能计成模型漏识别，也不能据此声称验证了完整采集召回。
- 中文主指标用规范化 CER，中英混说补充字/词混合错误率；单列人名、术语、数字、否定词等关键内容错误，保留插入/删除/替换明细。规范化口径提前冻结，不能为了候选得分把关键差异抹平。
- 同时报告按字数加权的总体分、各事件分与事件等权汇总，避免一段长音频主导全部结论；另列无声/噪声误转写，不把空参考纳入 CER 分母。
- 同机串行实测、固定输入和配置，记录冷启动与热运行、真实处理速度、P50/P95 延迟、峰值物理内存、模型下载体积/落盘体积/运行时增量、能耗与计量边界。重复/随机次序降低背景负载与温度影响，保留原输出、版本和结果指纹。
- 最终提供准确率与资源成本的取舍曲线和推荐场景，综合推荐不预设人为加权总分；是否更换生产模型属于另一个待拍范围决策。

## 候选初筛资料（2026-10-24，一手资料；未实跑）
以下是最初初筛摘要；经过用户要求的广搜后，以 [完整调研报告](../../research/2026-10-24-local-cpu-asr-survey/REPORT.md)的扩充名单、CPU 证据和待验证项为准，不能将这五条当最终候选范围。

- [Qwen3-ASR 0.6B / 1.7B](https://huggingface.co/Qwen/Qwen3-ASR-0.6B)：多语种及中文方言；需核查 Mac 的运行时和量化部署，不套用官方高并发 GPU 吞吐作为本机性能。
- [Fun-ASR-Nano](https://huggingface.co/FunAudioLLM/Fun-ASR-Nano-2512)：约 800M，中英日及中文口音/方言；模型卡给出 CPU 路径与 GGUF 社区运行时链接，实际性能和分发依赖待验证。
- [Whisper / whisper.cpp](https://github.com/ggml-org/whisper.cpp)：可对比 small、large-v3-turbo 等规模；官方项目支持 Apple Silicon、Metal/Core ML 与量化。每个模型、量化、后端视为独立实验配置。
- [Paraformer / sherpa-onnx](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/offline-paraformer/index.html)：现有运行时支持的中英/粤语与小型 INT8 候选，部署改动可能较小，效果须实测。
- [Apple SpeechTranscriber / SpeechAnalyzer](https://developer.apple.com/videos/play/wwdc2025/277/)：苹果官方说明模型下载后在设备上转录，可评估系统本地引擎；设备/系统/语言支持、资源归属与额外下载体积需要单独核实。

## 指标与验收建议 v1（2026-10-24，方案说明，未视为用户确认）

### 执行口径
- 约 10 组独立真实活动，历史使用分布为主、兼顾难例；保留各音源和可追溯时间，音频/答案/归一化规则先冻结，候选结果不反向改变评分口径。
- Agent 负责答案核验，保留精转初稿、修订与不确定区间。报告可评分覆盖率、疑难排除时长和原因；空参考、缺失原声、模型返回失败分开表达，不能删除失败样本后只报成功结果。
- 先测同机 CPU / 2 线程 / 相同生产分段；另列增加线程或模型推荐分段的效果和成本。主结果不混用 GPU/Metal/ANE。
- 每个事件报告成绩及相对基线差值，同时报告按参考字数加权的总体分和事件等权结果。性能预热后重复至少 3 轮、轮换顺序，冷启动独立记录；冻结原输出和配置。约 10 个事件的差异不能包装成通用模型排名。

### 主指标
| 类别 | 指标 | 口径 |
|---|---|---|
| 识别质量 | 中文 CER | 替换、删除、插入次数之和 / 参考字符数；分列三类错误；中英混说补充中文按字、英文按词的 MER，不混淆分母。 |
| 关键信息 | 关键内容错误数 / 10 分钟可评分语音，及关键项准确率 | 在跑候选前标注名字、术语、英文缩写、数字/时间、否定表达等；核对漏掉、识别错和凭空添加。统一关键项对齐/匹配口径，不能用关键词命中或 LLM 总体印象替代。 |
| 漏识别与幻觉 | 删除率、整句漏识别、无声/噪声区误转文字数或次数 | 无声区不进入 CER 分母，单列时长与错误；同源重复文字另列。区分分段/VAD 与识别模型造成的损失。 |
| 速度 | RTF、P50/P95 分段处理延迟、模型加载/首次结果延迟 | RTF=处理时间/音频时长；95% 分段完成时间的 P95 反映慢尾。模型输入就绪后的等待与生产切分/队列等待分开测。 |
| 内存 | 活动峰值物理足迹、加载后/闲置常驻、长回放趋势 | 包括实际进程树，注明 mmap/共享页与 swap；权重体积不是内存占用。 |
| 体积 | 必需权重、下载传输量、落盘量、运行时与最终分发增量 | 统一十进制 MB/GB 或明确 MiB/GiB；当前 ASR 权重约 239 MB、含 VAD/词表约 240 MB作为体积参照。 |
| 计算与能耗 | CPU 秒/语音分钟、同量输入的能耗相对基线指数、空闲成本 | 当前 SenseVoice 定为100；能耗计数的覆盖边界与系统背景负载需记录。有可信能量读数时才报 J/分钟，不把 macOS 进程计数当电池续航。 |
| 稳定性 | 失败/超时/空结果/崩溃计数，长回放内存或延迟增长 | 保留失败输出及原因；运行成功但有声区返回空文字，仍计入识别错误，不能只算作调用成功。 |

### 建议的判断目标
- 首要目标：显著改善粗转准确率与关键信息保真。暂建议相对当前基线 CER 降低至少 20%，争取 30%；这是待基线测量后冻结的业务升级目标，不是已知模型成绩，也不是 ASR 行业统一标准。例如基线 12% 到 9.6% 为相对改善 20%、下降 2.4 个百分点。
- 关键内容错误应同步减少；总 CER 下降却使数字、否定等重要内容明显退化的候选不能直接推荐为升级。每事件退化与错误样例要可见。
- 速度底线是能跟上实际持续输入、包括双来源负载而不持续积压；建议热运行单来源 RTF 争取不高于 0.25，为双来源与后台负载留余量。多来源需另外测实际调度容量，单个 RTF<1 不等于整条链路容量通过。
- 内存、体积和能耗先给实数与对基线倍率，不在基线未测时发明资源硬阈值。展示同成本准确率收益，以及增加成本能换来的额外收益；避免随意权重加总后宣称一个总分冠军。
- 只有约 10 组且答案自动核验，接近的分数按逐事件差异、关键错误与答案不确定区间做敏感性判断；改善小于证据可支持的范围时不判定明确胜出。
