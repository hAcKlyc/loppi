## 决策台账

### D1：本轮以干净转录为分析前提
- 定了什么：把讨论集中在场景、业务语义、用户收益与结果呈现，不把识别质量问题当作拒绝分析的理由。
- 为什么：用户要先明确值得让 LLM/Agent 做什么，之后才可能形成 prompt/skill。
- 用户原话：「在已经有明确、干净的转录上下文的基础之上，通过大模型或者 Agent 去做哪些处理和加工，去提炼哪些东西是能够产生真实价值的？」

### D2：自动消费需要独立研究
- 定了什么：主动查询/导出与用户没有主动需求时的自动提炼同时研究；不把上一轮的交接稿建议当作已拍定路线。
- 为什么：用户进一步强调无人管理的产品习惯，需要回答系统主动替用户完成什么以及何时值得占用注意力。
- 用户原话：「另一方面，在他没有关注的情况下，我们能够从其中提炼出哪些内容，或者用大模型做哪些事情是真的有价值的。」

### D3：先会议，兼顾三种形态
- 定了什么：正式会议是本轮主要分析对象；两人对谈和自言自语用于比较加工重点，不直接等同业务用途。
- 为什么：避免用一个笼统会议摘要覆盖所有声音，也避免只按参与人数套模板。
- 用户原话：「1. 典型的会议：这是一种特别明确的场景。\n2. 小会：比如两个人之间的对谈。\n3. 自言自语：比如我自己做某件事情过程中的记录。」

### D4：优先研究团队管理、项目推进与复盘
- 定了什么：正式会议的分析围绕管理者/项目负责人，不以产品研发需求交接为唯一主场景。
- 为什么：用户在三类会议样本中明确选择这一项；需进一步分析跨会进展、依赖、责任、判断与后续结果。
- 用户原话：「团队管理、项目推进与复盘」。

### D5：先定义通用事件理解，再进入具体场景
- 定了什么：产品讨论采用通用事件信息与具体场景加工的两层结构；之前的管理场景分析作为场景层的例子，不能代表 hear 的全部定位。具体字段与触发规则尚未拍定。
- 为什么：用户进一步指出 hear 是 context 的通用工具，希望所有粗转录事件先获得通用理解，业务会议等具体类别再开展相应动作。
- 用户原话：「本质上我们是 context 的通用工具，都是基于一大堆粗转录文本来输出内容。」
- 用户原话：「通用的视角来看，对于粗转录音频生成的事件，哪些是它的 meta 信息？」
- 用户原话：「第一次分析的时候的一个子类就是去 打上这个具体场景的分类或者标记。然后在执行针对这个场景下的细分动作吧？」

### D6：用真实较长粗转录制作扩展 JSON 样例
- 定了什么：读取一份真实长事件粗转录，核实当前模型输出格式，在其基础上扩展完整 JSON，供用户继续讨论字段；不改应用实现。
- 为什么：用具体内容检验结构是否必要、是否重复，而不继续停留在抽象字段列表。
- 用户原话：「你去读一下真实的这个粗转录的一份数据，时间长一些的那种。你来尝试作为例子输出一个完整版本的 json。我在根据这个跟你讨论修改方式。（在现有输出 json结构的基础上扩展）」
- 产物：[真实粗转录 JSON 样例说明](../../research/2026-10-23-event-json-example/README.md)。当前拟合按约 15 分钟候选续接；本次离线组装一个约 52 分钟现有事件，不冒充原始线上模型请求/响应。

### D7：保留三类扩展，试写 500 字内总分式摘要
- 定了什么：用户明确认为 topics、keypoints、mentioned_objects 有用，保留在样例中。按现有命名保留 `key_points`；本次试版先移除其他扩展项，以 `summary` 承担整场连贯语义描述，前两三句概括主题，再适度展开，一段文字控制在 500 字以内。
- 为什么：减少分散的语义描述，强化单一摘要的整体理解价值；先让用户看具体版本再讨论。
- 用户原话：「topics、keypoints、mentioned_objects 这三个是有用的可以留下。」
- 用户原话：「summary 其实相当于就是唯一一个语义化的用一段文字来描述这个讨论。那我觉得它应该可以用总分模式，现有一个两三句话描述在摘要主题，然后在稍微详细的讲讲？但整体控制在 500 字？你试着这个思路改一版看看」
- 结果：第 2 版摘要为 355 字符，含标点等；保留第 1 版以供对照。仅调整样例，尚未修改生产的 240 字符限制。移除其他字段是本次试版的解释，不等于永久取消场景分类能力。

### D8：沿用窗口更新，数据完整保存，前端展示另做
- 定了什么：本次直接扩展既有窗口拟合输入与输出，把上一轮摘要和结构化结果传入并更新，不新增事件级理解任务。summary 不设业务字数硬截断或超限置空，界面用行数省略。三个新增字段完成存储、上下文续接、引用及失效链路，不做新的前端展示。
- 为什么：用户明确选择较小且可复用的处理范围，优先把数据形成和积累做好，避免同时引入独立整场分析与新增界面。
- 用户原话：「我觉得先沿用现在的窗口分析就行，把上一轮的摘要和结构化结果带进去更新。」
- 用户原话：「界面上设置摘要展示超过几行剩下… 就可以了，数据层面不要限制。」
- 用户原话：「本次新增的数据不需要再界面上单独展示，先做好存储和链路处理，展示前端是之后的需求」
- 解释：此前 500 字目标可保留为 prompt 的简洁写法建议，不用于拒绝、截短或清空合法内容；当前两行省略可直接沿用。内部字段如何持久化与传递由实现选择，不为没有消费端的字段额外新增展示接口。

## 张力时刻

- 摘要第 4 版校正：用户指出「这是为了快速定位这是说的那件事，我感觉需要真实的细节，不能全部抽象描述。」摘要的首要目标是具体事件的辨认与快速理解，必须保留真实对象、指标、案例等线索；不能为了与 key_points 去重而变成抽象议题总纲。本次只改 summary，关键点保留，500 字内约束继续适用。
- 样例第 3 版：用户追问 summary 与 key_points 的重复，并要求「两个你一块思考修改。」因此同步调整两者：摘要保留全局脉络和主要分歧；关键点提供可独立取用的具体清单、方法、流程或问题，避免再次概括各个话题。原文依据保留，未更改三个扩展项的结构。
- 最新校正：上轮过早围绕管理会议展开默认产物；用户要求先把通用 context 层讲清楚，再把业务分析作为可选择的场景能力。输入前提也由干净转录回到粗转录，通用推断应允许未知和修订。
- 用户把问题从“用户主动拿记录生成工作材料”进一步推向“用户什么都不管时，系统应该持续提炼什么”。这是一处范围校正；此前报告的首选建议仍是候选，不能视为用户认可。
- 分析判断：参与人数/对话形态能帮助识别输入，业务目的、本人责任和工作阶段决定应该生成什么；同样两人对谈可以是决策、反馈、访谈或闲聊。
- 分析判断：自动加工与主动打扰是两道不同的门。项目变化值得沉淀，不意味着需要通知；不确定项也不应默认变成用户必须清空的确认清单。
- 分析判断：复盘应还原当时的目标、理由和假设，再对照后续结果证据；仅凭发言不能判断实际完成、真正根因或员工能力。

- 最新样例收敛：三个扩展项 `topics`、`key_points`、`mentioned_objects` 保留；总分式单段摘要试用 500 字内。之前六维框架是背景，具体输出以第 2 版样例供讨论，不把全部维度继续视为必须输出。
- 最新通用层建议：来源与时间、内容概览、内容结构、提及对象、交流语境与用途线索、证据与可解释范围；最小默认产物与具体词表尚未确定。
- 输出形式建议：用于程序定位/筛选/关联的信息明确结构化；标题摘要保留自然语言；章节、要点、提及对象采用列表结构承载开放文本与证据。用户当前在询问划分，尚未拍定 schema 或词表。详见通用框架第 10 节。
- 最新分层建议：场景候选帮助选择加工；结合内容与输入条件决定是否生成。场景任务可取回相关原文，不只读摘要；关联历史属于有材料时的扩展。
- 以下为此前管理场景的候选，不作为所有事件的默认行为。
- 管理场景候选主线：项目当前明确约定了什么、后来改了什么；哪些变化值得本人介入；下一次沟通与复盘如何直接续接。
- 候选产物：带出处的决定/约定/依赖、跨次变化、具体待决问题、复盘事实底稿、可取用的同步稿。
- 候选默认体验：后台整理，场景内按需出现；少量汇总可选；及时提醒单独设门槛。没有新后果可以没有卡片，不设默认待确认清零压力。
- 候选 Skill 契约：会话事实整理、项目变化核对、依赖与待决识别、相关工作续接、复盘事实准备、个人思考整理。仅定义业务任务，不确定架构或调用次数。
- 仍未决：本人/项目关联方式、默认展示入口和时机、提醒范围、历史与外部读取边界、首个独立交付及验收样本。

## 必赢场景

当前交付的可验证场景：同一长活动跨多个窗口，后续窗口接收到已保存的摘要与三个结构化字段；新结果更新后保留仍有效的旧信息、合并重复内容，引用仍指向正确原文。合法长摘要完整存储，卡片按行省略；数据修改或删除后不再使用已失效的派生结果。前端不新增结构化内容展示。

## 技术前提

- 已核实：首轮研究已核验 hear 0.1.5 的事件、精转、人物、Mark/评论、截图、回放、CLI搜索与导出；见[能力基线](../../research/2026-10-23-hear-context-consumption/hear-baseline.md)。
- 输入前提：上轮用干净转录隔离业务价值讨论；最新改为粗转录事件。分析需区分采集事实、文本中的明确表达和模型推断，容纳后续精转/修正，不把粗转错误继续放大。
- 当前技术前提：已选择既有窗口链路；需落实稳定引用、结构化结果的有效性与迁移。本人识别/角色配置、跨项目长期状态与外部读取属于先前场景探索，不是当前存储交付的前置要求。
- 对决策的影响：明确区分单次谈话能提取的事实、跨次记录支持的变化，以及需要外部工具才可确认的执行状态。
