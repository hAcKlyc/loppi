## 决策台账
### D1: 配置驱动的识别策略与双输出
- 定了什么：已配置 LLM 时希望用 LLM 理解截图，输出图片说明和完整 Markdown 转录；无 Key 时保留本地 OCR。
- 为什么：原始 OCR 只逐行拼接文字，不能说明画面含义、缺乏结构。
- 用户原话：「如果我已经配置了 LLM 的话，就走 LLM 来识别呢。我觉得可以输出两部分，一部分是对图片的摘要说明，这是个什么图片以及里面表达了什么信息。然后是对于图片内部文本的完整转录（md 格式）。而如果用户没配置LLM 的 apikey 的话，就是你现在的逻辑。」

## 张力时刻
- 配置 API Key 不等于模型支持图片输入，须先核实当前 DeepSeek 接口能力，不能把 OCR 后文本润色冒充看图理解。

## 技术前提
- 已核实：现有 LLM 供应商固定 DeepSeek，地址 https://api.deepseek.com/chat/completions；cloud.rs 的请求为文本 messages，用于事件整理。当前截图在 moments.rs 保存 PNG 后同步调用本地 Vision，存 ocr_text/ocr_state；无截图云端任务或摘要字段。
- 已核实：原架构文档承诺截图不因现有 LLM/ASR 任务外发；本功能会增加用户已提出的截图云端理解用途，必须在配置与说明中表达清楚，不能偷偷复用旧用途描述。
- 已核实（2026-10-18）：src/CloudKeyInput.tsx:43、WorkspaceViews.tsx 使用 deepseek-flash；DeepSeek 官方 https://api-docs.deepseek.com/guides/vision/ 明确支持图片、截图文字与图表理解，可通过当前 Chat Completions 的 image_url/base64 内容块发送。
- 已核实：官方图片预处理会按面积缩放，极小文字不能保证忠实完整，应保留原图、要求无法辨认处标记而非补写。
- 待核实：接入既有 cloud_tasks 对截图任务的复用范围（需 PRD 技术核实），此轮不新增代码/云端请求。
- 对决策的影响：须明确使用哪个支持图片的模型，以及不支持图片时的行为，才能形成可执行 PRD。
