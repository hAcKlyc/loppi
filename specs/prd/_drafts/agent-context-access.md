## 决策台账

### D1：同机 Agent 是核心场景
- 定了什么：本次方案以同机 CLI + 本机 MCP 接入为核心；远程访问不作为必要架构。
- 为什么：用户进一步收敛需求；避免为并非核心场景的远程连接引入网络监听、配对和部署负担。
- 用户原话：「核心场景应该是当前设备上安装的其他的 Agent 访问就行了。甚至都不需要局域网」

### D2：本轮先做设计
- 定了什么：先核实源码现状，再提出能支撑 Agent 发现、取回、核对 context 的整体方案，明确现有与新增。
- 为什么：已有 CLI/IPC 与事件理解积累，应复用权威数据源和生命周期。
- 用户原话：「围绕这个背景，你先了解一下当前的现状，然后帮我完整设计一下相关的方案」
- 用户原话：「因为这些工具都是给 Agent 用的，所以你需要从 Agent 的视角来思考应该怎么去设计。」
- 用户原话：「（本质上，CLI 和 MCP 应该配置相同的 skill，结构大概是一样的。）」

## 张力时刻
- 用户先选择自己的设备通过局域网或私人网络，随后进一步校正为当前电脑上的 Agent 即可。以最新收敛为准。
- 初步发现：现有 CLI 已存在，MCP 尚需源码确认；目标是统一消费契约，而非重复建设两个后端。
- 核实后的关键判断：现有 topics/key_points/mentioned_objects 已持久化，但未通过当前事件 DTO 暴露；MCP 仅包裹当前 CLI 不足以完成目标。
- 生命周期事实：现有 CLI 按需启动不自动开麦，但 Core 仍启动处理线程，可能继续已有任务；不能把它解释为无后台处理副作用的读取模式。

## 必赢场景
建议验收场景：用户在同机 Codex 等 Agent 里询问今天/某段时间/某个话题的经历，Agent 能发现 hear、少量读取候选事件、按需取回带时间和出处的当前有效原文，交付有依据的答案；hear 继续原有采集与整理。覆盖 MCP-only、CLI+skill 和两者共存。
