# 讨论台账：手动确认事件结束与详情操作收纳

## 岔路清单
- [x] 支持用户在「等待事件稳定」时手动确认事件结束 → 目标明确，待核实结束边界和现有流水线契约。
- [x] 事件详情外显操作收进更多菜单，状态移到顶部 → 用户明确要求；待核实当前操作范围。
- [x] 不改时间直接确认的自动续接权限 → 用户确认事件完成，后续自动整理不再将其作为可续接/重组目标。
- [x] 未改时间的处理 → 保留现有 LLM 识别结果，结束稳定等待，进入既有后续处理。
- [x] 默认时间与尾部矫正方式 → 预填事件当前起止时间，用户可以手动修改；不默认改成点击时刻，不自动推断补齐整场边界。
- [x] 修改时间后的识别 → 重新切割并重新使用 LLM 识别，非只保存边界或只启动精转。
- [x] 修改后的起止时间是参考范围 → 允许 LLM 重新调整，输入明确标注是用户手动调整过的时间。
- [x] 修改时间重新识别后的完成语义 → 本次成功产出的所有事件均视为已确认结束，不再自动续接，无需再次等待稳定，直接进入精转。
- [x] 操作收纳范围：事件级管理操作全部进更多，播放、正文切换与现场记录保持内容区直接操作。用户授权开发后按既定方案执行。

## 决策台账
### D1: 增加人工结束入口
- 定了什么：事件详情顶部显示状态，「待事件稳定」可点击，二次确认后结束事件，进入后续处理。
- 为什么：会议结束后用户可能需要立即查看内容，自动判断结束的等待不能阻塞主动需求。
- 用户原话：「我刚结束一场会议，其实我希望能立刻看下这个内容，所以会想要手动触发事件已经结束了，而不是等待到下一次事件完成识别。」

### D2: 详情操作收纳
- 定了什么：事件详情目前外显的功能移入更多菜单，状态放在顶部区域。
- 为什么：给事件内容和可操作状态腾出主要视线位置。
- 用户原话：「我希望点击事件弹出的弹窗上，外显的功能，都放到更多菜单里。」
- 用户原话：「把状态写在顶部区域，如果是「待事件稳定」应该是可以点击，弹窗提示 是否确认该事件已经完成，我点个确认。这个事件就算完成可以走后续的精转录等等流程了。」

### D3: 确认弹窗承载人工起止校正
- 定了什么：点击顶部「等待事件稳定」后，确认弹窗展示可编辑的事件开始和结束时间；默认值沿用当前事件范围。未改时间时确认已有范围；修改后以新时间为参考重新整理，成功后按模型结果结束并启动后续处理。
- 为什么：人工指定会议范围直接解决识别边界滞后的问题，避免自动把截止点延长到点击时刻，吸收不属于会议的内容。
- 用户原话：「点击「等待事件稳定」的这个确认弹窗，下面有一个事件的起始时间和结束事件的数值呀。默认就是当前的这个状态，但用户可以手动改起始和结尾，这样人工矫正了一次。」
- 对既有建议的纠正：不采用默认补齐到点击时刻方案；尾部是否纳入由用户通过结束时间明确表达。

### D4: 未改时间直接确认，保留识别结果并完结当前事件
- 定了什么：提交起止时间未变时，用户直接确认当前范围与已有 LLM 结果；该事件不再参与后续自动续接/重组，结束稳定等待并进入既有精转处理。这里的「已完成」指事件边界已确认，不代表精转任务已完成。
- 为什么：当前范围已由 LLM 整理，人工确认后没有必要再等后续内容来判断关系，也没有必要重复调用 LLM。
- 用户原话：「若用户没有改过时间，而是直接选择确定：可以直接把这个时间状态置为“已完成”。在计算下一个时间时，就不需要再加它了，因为它已经和前后没有关系了，用户已经手动确认了。」

### D5: 修改任一端时间，需要重新切割并重新做 LLM 识别
- 定了什么：提交的起始或结束时间发生变化时，按新范围重新切割、重新使用 LLM 识别，更新相关事件内容；不只沿用原摘要并修改边界。
- 为什么：用户更改范围意味着原识别结果的依据已变化，需要按新材料重新整理。原声、已有粗转、可复用精转仍属基础事实，不因「重来」全部丢弃或重跑。
- 用户原话：「若用户手动更改了时间（无论是起始时间还是结束时间）：那就重新切割，重新使用大模型去做识别，相当于重来一遍。」
- 输出沿用现有 LLM 事件重整语义，不强制固定一个事件；本次成功结果统一视为已确认结束，见 D7。

### D6: 人工调整时间是参考，明确标注用户来源
- 定了什么：修改后的起止时间作为本次 LLM 重新整理的参考范围，模型可结合内容调整最终边界；输入明确告知这些时间是用户手动调整过的。
- 为什么：用户希望重新使用模型判断活动边界，人工时间携带意图，不替代模型切割；拒绝 Agent 此前推荐的硬边界方案。
- 用户原话：「作为参考，但提示 LLM，这是用户手动调整过的」
- 对既有建议的纠正：不锁定模型输出必须等于用户新填的起止；不把此分支静默实现为固定一场的摘要重建。

### D7: 修改时间重新整理后的结果也全部确认结束
- 定了什么：修改时间并重新整理成功后，本次产出或更新的事件统一视为已确认结束，后续自动整理不再续接或改动；无需再次确认、无需再次等待稳定，直接进入既有精转处理。仍可由用户主动编辑或重新整理。
- 为什么：用户这次操作已经表达了事件结束的意图，LLM 重新识别只是在更新组织结果，不应把事件重新送回观察等待。
- 用户原话：针对「新结果是否也一律视为已确认结束、以后不再续接」回复「确认，是的。」
- 完成时机：新的结束事实与重新整理成功结果一起生效；识别失败仍保留旧结果，提交受理不提前宣称新结果已完成。

## 张力时刻
- 用户纠正了默认补齐到点击时刻的建议：默认沿用事件当前边界，给用户编辑起止时间的机会，由人工一次校正范围。
- 已核实：「等待事件稳定」同时承载观察等待与本地/整理积压，不能把确认结束简单实现为改状态或调用重新精转。
- 用户收敛成两个分支：未改时间直接确认已有结果；改时间则重新切割并重新 LLM 识别。这替代此前仅讨论「改边界后补摘要」的方案。
- 用户拒绝硬边界建议，指定人工修改过的时间仍作为 LLM 参考，并要求明确提示时间来源。
- 用户确认：改时间重新识别的新结果也一律结束，不再续接，关闭了「重识别后是否重新等待稳定」的岔路。

## 必赢场景
用户刚结束会议，打开该事件详情，点击顶部「等待事件稳定」，在确认弹窗中查看并按需校正当前事件起止时间。未改时间则立即确认当前事件结束并进入精转；改时间则以用户调整时间为参考重新 LLM 整理，成功后的结果统一确认结束并进入精转。两条分支都不再等待后续自动识别判断结束，详情能看到处理进度与结果。

## 原子交付边界
- 本 PRD 必须一次完成并统一上线的范围：手动结束契约、详情顶部状态、操作移入更多菜单、确认后已有处理链路和状态反馈。

## 技术前提
- 已核实：Core 是数据和状态唯一 owner，前端「等待事件稳定」来自精转规划投影，没有独立会议完成状态；自动规划通常等待末尾15分钟或后续同源事件，并检查本地/候选待办。
- 已核实：自动事件可跨窗延长；已有人工边界锁可以阻止常规自动延长，显式用户重组可以重新调整人工边界。
- 已核实：正常 ASR planner 复用当前任务覆盖；「重新精转」会清除当前引用并创建付费新运行，不适合代替结束操作。
- 已核实：摘要/理解在事件整理时基于粗转生成；精转完成不自动重建摘要。更多目前实际进入拆分/合并/取消标注管理弹窗。
- 证据：[技术核实](../../research/2026-11-02-manual-event-completion.md)。
- 已核实：现有 `edit_event_in` 仅在起止/来源发生变化时才锁边界、清空摘要/理解并规划 ASR；时间完全不改时不会启动精转，因此不能直接把本入口接到普通编辑保存。
- 已核实：现有 `reorganization` 使用参考时间，可调整边界/邻近事件，发布结果不锁边界，但会以 `manual=true` 立即规划精转；可复用其重新识别与精转衔接，人工边界和完成语义仍需明确。已有固定边界 `rebuild` 只重建摘要/理解，不重新切割，也不能直接代替该分支。
- 待核实：选定范围末端尚未封存/粗转未齐时，重新识别怎样覆盖本次输入；重新整理对其它已确认事件的权限需与 D4 的保护语义协调。
- 对决策的影响：两条分支的完成和自动续接语义已确定；待核实事项需明确进入执行文档前的技术核实或开发成功标准。后续均复用既有 Core、任务队列和 ASR 引用，不新建平行处理系统。
