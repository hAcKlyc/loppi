# hear 方案自审

日期：2026-09-21。范围：[PRD](prd_0.1.md)、[RFC](tech_rfc_0.1.md)与仓库说明。方式：同一作者完成一轮需求回溯、跨文档一致性、故障路径和技术依据检查；不是独立第三方评审，也没有运行产品实现。

## 结论

已整理为独立产品方案，可作为后续产品收敛和技术验证的基线。已发现的文档错误与歧义已修正；PRD保持`draft`，RFC保持`proposed`。尚不能按冻结需求直接进入完整开发或据此宣称性能达标。

## 本轮已修正

| 问题 | 修正与落点 |
|---|---|
| 旧内置功能方案容易带入MyAgents版本、Session/Sidecar及存储约束 | 独立核心拥有产品生命周期；MyAgents仅为外部消费者。见PRD第1/11节、RFC第2/3节 |
| 24小时采集、原声兜底和正式记录保留容易混用 | 分别定义运行模式、有限回溯窗口、正式保留；删除旧“自动记录统一7天过期”的默认结论。见PRD第1/7节 |
| 讨论建议与已确认需求混杂 | 数值集中为RFC候选表；真正影响产品行为的未决事项只在PRD D1–D6维护 |
| 无人声降档可能被实现为关闭采集，丢失弱语音/句首 | 优先降低分析负担；稳定原声采集，VAD不决定立即删原声。见PRD第6节、RFC第5/6节 |
| 切割、文件封块、会话归组及删除被混为一体 | 区分物理文件、ASR单元、事件引用区间；保留真实时间与缺口，先组织后按规则清理。见RFC第4/6/8节 |
| Mark“成功”可能夸大已保存声音，延迟评论可能错位 | 明确锚点不随评论提交移动；动作提交与媒体持久化水位分开，未来音频待补齐。见PRD第3/5节、RFC第8节 |
| 当前设备generation若作为全局校验，会误拒绝历史任务结果 | 区分来源流身份和任务执行代次，按输入revision/attempt/删除状态提交。见RFC第3/4节 |
| 事件重组可能使旧引用悄悄指向不同内容 | 拆分返回后继集合，证据范围保持稳定；模型不能覆盖人工更正。见RFC第4节 |
| 只异步清索引会让已删内容暂时继续可见 | 所有读取按当前元数据过滤；部分删除覆盖共享媒体、副本、派生结果和迟到任务。见RFC第8节 |
| 泛称Windows OCR模型、Windows10能力和模型“低功耗”依据不足 | OCR留为待选；按官方API/样例区分版本；RTF限定硬件/线程，预算明确未实测。见RFC第5/6/10/12节 |
| 多份草稿反复维护同一规则会漂移 | PRD负责产品语义，RFC负责技术与数值；不复制旧HTML及历史草稿为另一套权威文档 |

## 验证与证据

- 复核存储、PCM/截图缓冲、CPU积压和电池容量公式；区分十进制GB与二进制MiB、单核等效与整机功率。
- 对照官方来源核对平台能力和模型基准口径；引用集中于RFC第12节，不能据此推定hear实测表现。
- 检查本地文档链接、章节锚点、Markdown结构和提交范围；本轮只提交设计文档与仓库说明，不包含应用实现、模型或用户媒体。
- 场景推演覆盖正常会议、短讨论、截图后评论、睡眠/重启、设备切换、空间不足、删除与迟到结果；这是设计审查，不是已执行的验收测试。

## 仍需收敛

产品决策以[PRD第10节](prd_0.1.md#10-待确认产品决策)为唯一清单，本文件不复制第二套默认值。尤其是自动会话如何成为正式保留内容、长期容量与期限，会直接影响体验和磁盘策略，不能留给实现者猜测。

技术验证以[RFC第11节](tech_rfc_0.1.md#11-验证门槛草案)为准。尚缺真实机器上的功耗、内存、丢帧/尾损、中文与混说识别质量、会话归组质量，以及云端相对收益测量；这些都未被本次文档自审视为通过。
