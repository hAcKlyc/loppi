# 每天定时关闭和开启录制

## 执行须知（给空 session 的你）

先读 [ARCHITECTURE](../ARCHITECTURE.md) 的所有权、采集生命周期和统一入口章节，以及 [算法说明](../tech_docs/algorithms.md) 的采集、封块和恢复约束。用户于 2026-10-20 确认：「确认，按这份 PRD 开始开发。」核心规则和本文默认细节、架构方案均已接受。原讨论台账已完整吸收并删除。

本 PRD 是一个原子交付单元：设置、协议、持久化、Core 执行与恢复、所有录制入口状态、迁移、测试及文档一起完成。开发批次只组织实现、验证、review 和 commit，不允许仅上线设置而没有后台执行。本文引用真实文件和符号，避免用易漂移行号代替技术事实。发布门槛见第 6 节，未通过不得标记交付完成。

## 1. 背景与必赢场景

用户希望在设置页配置活跃周期，例如晚上几点到几点不录制，其他时间录制。讨论进一步明确：

> 相当于是在设定的那个时间点，进行了关闭和开启的操作。如果本身已经打开不会特意再关闭掉等等。

因此，功能是每天两个定时动作，不是持续限制某个时段的录制权限。用户在夜间点击录制，就是正式开始；不需要临时放行，也不能被循环检查再次关闭。

必赢场景：设置每天 23:00 关闭、08:00 开启。23:00 正常停止；23:30 用户手动开启后持续录制；08:00 已在录制则不中断、不新建一次启停；下一次 23:00 才再次关闭。若睡眠错过 08:00，09:00 恢复后补开启；若跨过多个时间点，只补最近一次。已执行的关闭不能在重启后再次覆盖用户随后做出的手动开启。

## 2. 一次交付范围与反向边界

交付内容：设置页的启用开关及两个时间输入、持久化配置、Core 中的边界动作执行、遗漏动作恢复、手动操作排序、统一状态反馈，以及对应迁移、回归与真实客户端验收。

控制当前已启用的麦克风和电脑声音，保留各来源的独立开关。定时开启不替用户打开已禁用的来源。定时关闭只停止新增音频采集；已有封块按原流程完成落盘、入库和分析，原有粗转、精转、整理等任务继续。主动截图、笔记、回放与浏览不受影响。这些补充默认值已随成稿接受。

不包含按星期配置、每天多段规则、云端同步、远程控制、唤醒电脑或在用户完整退出后自行拉起应用。不修改音频保留、ASR 请求身份、付费任务重试、来源权限或空间保护政策。不承诺系统睡眠/关机期间录制，也不伪造这段时间的音频。

## 3. 产品行为与数据契约

### 3.1 设置与保存

在现有设置页“记录”区域增加“定时录制”：启用开关、“每天停止录制”及“每天开始录制”两个时刻。按分钟配置，使用 24 小时制，支持跨午夜。为避免一日同时产生相反动作，两个时刻相同禁止保存，提示“开始和停止时间不能相同”。

默认方案：新用户和升级用户均关闭；首次编辑可预填 23:00 停止、08:00 开始作为可修改示例，未经用户保存启用不得执行。关闭后保留所填时间。

保存成功后，从严格晚于保存时刻的下一个时间点开始。首次启用、重新启用和修改时间均不立即改变当前录制状态，也不补执行新配置生效前的动作；关闭定时开关同样不启停录制，停用期间不累计遗漏动作。界面明确提示“保存后从下一个时间点开始执行”。

设置页规则开关立即提交，开关与说明均显示已生效配置。时间组合在独立编辑弹窗中提供保存时间/取消；关闭时编辑时间不启用规则。保存失败保留输入并显示可重试错误，不假装已启用；重复请求不能重置已生效规则的执行起点。并发修改沿用现有修订检查，冲突时重新读取，不静默覆盖。此交互修订由 2026-10-20 用户确认，见 devplan_261020_settings-interactions.md。

### 3.2 定时与手动操作

| 场景 | 结果 |
| --- | --- |
| 到达停止时间，正在录制或启动中 | 通过既有停止流程收尾，停止两路已启用来源的新采集 |
| 到达停止时间，已经暂停 | 标记该动作已处理，保持状态，不重复停止 |
| 到达开始时间，暂停或尚未开始 | 设置正常的开始录制意图，实际采集仍遵循现有权限、设备、模型及容量条件 |
| 到达开始时间，已经录制或启动中 | 标记该动作已处理，不关闭再开启、不重建正常 session |
| 定时停止后手动开始 | 正常持续录制，直到后续手动操作或下一次定时停止 |
| 手动暂停后到达定时开始 | 按配置执行开始；手动操作不是永久取消定时规则 |
| 同一时间边界附近手动操作 | Core 先结算该操作之前已到期的定时动作，再应用手动操作；之后不回放更早边界覆盖它 |

“已是目标状态”同时考虑持久录制意图和正在启动/停止的真实状态。未收到音频并不等于需要再次执行开始，例如设备还在启动或既有来源恢复正在进行。

### 3.3 恢复、重复执行与阻断

用户明确接受：“恢复运行后补执行最近一次错过的定时动作，已经是对应状态就不用重复操作。”

持续启用的同一配置在睡眠、Core 中断、应用退出或重启期间跨过边界，恢复正常运行后只结算最近一次遗漏动作；更早动作一并视为已越过。跨数日也不能逐日遍历执行或产生启停风暴。不存在遗漏动作时不重新按当前时段计算开关，保留最后的手动操作。

动作的意图变更和“已处理”记录必须共同持久化。目标已经满足时也记录已处理，避免之后的手动操作被同一边界覆盖。提交前失败保持可重试；提交后崩溃由既有采集监督恢复，不再重复修改意图。

定时开启不会清除容量安全暂停，不替用户授权或弹出后台授权对话框。无法实际录制时显示已有具体阻断原因；不能显示“正在录制”。一旦开始意图已持久生效，来源恢复继续复用既有路径，不增加周期专用重试队列。空间保护仍按原有手动恢复规则处理。下一定时停止或用户暂停可正常撤销开始意图。

完整退出期间不执行动作、不自行启动应用；用户主动重新打开 hear 后属于恢复运行，可补遗漏动作。单独的 CLI 状态/历史查询或按需查询服务不构成恢复正常录制，不得意外触发采集，也不得提前消费未来需要补的动作。正常登录启动与主动打开应用的恢复入口须明确区分现有 `QueryOnly`、`SessionStopped` 语义；这属于本稿提出的完整恢复方案，已随成稿接受。

### 3.4 本地时间

默认跟随电脑当前系统时区，不另提供时区选择器。采用当地日历的每天两个时刻，不能把“一天”固定为 24 小时递增。

补充时间规则：同一时区内时间前跳，补最近一次遗漏动作；时间回拨不重复执行已经处理的同一日边界。夏令时不存在的当地时刻在跳变后的首个有效时刻执行，重复出现的当地时刻只执行一次。若两个动作映射到同一实际时刻，按原当地时刻顺序取最后一个目标，不能连做两个相反动作。

系统时区变更按新时区重新建立未来边界，当前状态保持不变，不把旅行产生的时差当作一串遗漏动作回放。保留已处理记录以防重启重放。系统时间不可用或转换失败时不猜测动作，保持现有状态并展示可诊断错误。这些边界规则是成稿默认方案，已一起确认。

### 3.5 状态反馈

设置显示已保存的每日规则及“下一次：今日 23:00 停止录制”之类信息。主界面、顶部和悬浮入口继续以 Core 的真实采集状态为准；定时暂停时可显示“定时暂停 · 下一次 08:00 开始”。手动恢复后应显示真实录制状态，不能因为时间仍位于夜间就显示休息中。

下一次动作是计划，不是成功承诺。被权限或容量阻断时显示实际原因，避免将“开始时间已到”伪装成采集成功。动作不额外弹出通知，不增加周期轮询来源；使用现有状态快照刷新。

## 4. 技术事实、方案与架构边界

### 4.1 已核实的基础

- `src/WorkspaceViews.tsx::SettingsView` 已有“记录”区域；GUI 经 Tauri 与 `hear-protocol` 调用 Core，不拥有业务数据库。
- `crates/hear-core/src/main.rs::capture_supervisor` 根据录制意图、暂停、容量、来源开关、模型和运行许可控制两个来源，持有已有启停、异常退避与睡眠处理。`CoreState::service_state` 和 `diagnostics::apply` 投影实际状态。
- `Store::handle` 的 `Start/Pause/Resume` 更新意图和缺口，`Store::mutate` 使用修订与请求回执保障重复控制。`Resume` 还可能清除容量暂停，不能无条件用于定时开启。
- `LaunchMode`、`allow_capture`、`quit_in_login` 与 `serve_one` 区分正常录制、查询启动和本登录显式退出。新增恢复能力必须明确衔接这些条件，不能仅看进程是否存在。
- `Store::new`、`storage::migrate` 维护 SQLite 与迁移；当前没有录制定时配置或边界执行记录，也未发现可直接复用的 Core 本地日历调度器。
- `src-tauri/src/entry.rs::EntryRuntime` 与 `src/CaptureStatus.tsx` 共用宿主状态；手动截图是独立的显式动作。

### 4.2 唯一 owner 与持久化

建议由现有 Core 执行定时动作，使用同一个 SQLite 权威状态与写事务。前端只编辑配置、显示结果；不得在 React 定时器、悬浮窗或第二个后台服务里承担执行责任。配置启用后，即使关闭主窗口或不打开设置页，正常运行的 Core 仍执行。

允许的最小新增状态：一份定时配置（开关、两个当地时刻、配置代次/生效起点），一份足以判断最近遗漏边界、去重和时区变化的持久处理记录，以及区分定时/手动暂停所需的原因事实。具体字段与表落点由开发阶段决定，但必须在现有 Store 中统一管理；不另建通用日历、任务库或无界执行历史。

由现有控制路径抽取/复用启停意图更新、媒体收尾和缺口维护。定时、手动及配置保存通过同一写入顺序串行裁决，拒绝过期配置计算出的边界。定时与手动暂停原因要准确，但不能新增一套与录制意图竞争的“夜间禁止录制”状态机。

允许扩展现有 IPC 的配置读写、结构化状态和必要的正常应用恢复信号，用于区分主动打开应用与纯查询；不得新增端口、服务或权限。配置保存复用请求 ID 与预期修订。实际采集异步收敛，不能用界面乐观更新替代来源回调。

### 4.3 资源、迁移与兼容

Core 内部日历计算与时间来源须可注入测试；使用平台日历/时区能力或项目适用的轻量库，禁止引入通用调度框架。生产循环只计算最近遗漏和下一边界，使用常数级持久状态，不按应用离线天数创建任务。持续运行时正常边界判定目标为 1 秒内，实际设备启停沿用现有有界截止时间，不承诺音频在整分钟零延迟硬切断。

配置、动作处理记录与意图写入事务不得包含原生设备启停或文件 IO。SQLite 失败时不能先执行设备动作再补写记录。系统睡眠期间没有执行承诺；唤醒后先补最近遗漏动作，再决定是否启动来源，避免先按旧意图启动后立刻停止。

旧数据库升级默认定时关闭，保留现有手动意图、来源设置、历史媒体、任务身份与清理墓碑。新增字段和协议版本按现有兼容机制统一处理；GUI、Core、CLI 的相关协议匹配必须在同次交付验证，不制造开发批次之间的临时兼容路径。

如果无法在现有 Core/Store、采集监督和 IPC 内满足这些保证，或需要独立调度进程、另一份权威状态、放宽退出/权限边界，应停止扩展并重新讨论，不能默默增加系统形态。

## 5. 关键决策及理由

| 决策 | 原因与排除的方案 |
| --- | --- |
| 每天一组关闭/开启时间 | 用户选择每天固定一段，不引入星期表或多段规则 |
| 边界动作而非持续时段限制 | 用户明确纠正：手动开始就是正式开始，持续限制会反复覆盖用户操作 |
| 目标已满足时只记录处理 | 避免重复启停与录音断点，并防止同一动作在未来覆盖新的手动意图 |
| 只补最近遗漏动作 | 恢复应符合最新意图，不回放数日启停历史 |
| 保存从下一时间点起效 | 用户明确选择，编辑设置本身不承担启停副作用 |
| Core 单一执行和持久边界记录 | 支持窗口关闭、重启和去重，无须新增进程或竞争状态来源；已接受的架构方案 |
| 默认关闭、系统当地时间、真实状态投影 | 保留升级前行为，降低设置负担；这些辅助默认值已随成稿接受 |

## 6. 验收与发布门槛

所有验收必须使用隔离数据和明确授权的测试环境，不以改动用户活跃录音数据库来验证恢复。

| 验收项 | 成功标准 |
| --- | --- |
| 默认与配置 | 升级后定时关闭；两个时刻可保存并持久化；同刻拒绝；保存失败、重复请求、并发修订不会错误启停或重置规则 |
| 保存起点 | 在示例夜间启用或修改配置，当前录制不变，仅下一未来边界执行；停用和重新启用不回补停用期间动作 |
| 正常定时与手动 | 完整跑通第 1 节场景；已录制时定时开始不换 session、不产生人为缺口；手动暂停可被下一次定时开始恢复 |
| 同时到期 | 手动操作与边界竞争按 Core 顺序裁决，已到期旧动作不能在手动操作后再次执行 |
| 恢复与幂等 | 跨一个/多个边界、跨多日、动作前后崩溃均只得到最近目标；已处理后手动改变再重启，不被旧动作覆盖；无操作也须记录处理 |
| 真实停止与封块 | 停止两路新增采集并完整封存已有尾块，正常解析/入库继续；不会清空媒体或取消已有云请求 |
| 来源与阻断 | 只控制用户已启用来源；权限缺失、模型未就绪、空间暂停均显示真实原因，不被定时规则绕过 |
| 生命周期入口 | 主窗口关闭后仍按时执行；正常登录/用户重新打开后补遗漏；完整退出不被定时唤起，纯 CLI 查询不开始采集、不消费遗漏动作 |
| 时间异常 | 注入跨午夜、时钟前跳/回拨、夏令时缺失/重复、系统时区变化，结果符合 3.4 且无重复或启停风暴 |
| 一致反馈 | 设置、主界面、顶部及悬浮入口在现有刷新周期内一致显示真实状态；手动夜间录制不显示“休息中” |
| 性能与回归 | 离线天数不影响待办规模；不增加无界轮询或状态历史；已有启停、来源恢复、容量保护与任务恢复测试通过 |

实现中必须验证：系统日历转换能覆盖当地时间跳变；Core 恢复排序不会先按旧意图启动采集；主动应用恢复与纯查询可被既有 IPC 可靠区分。验证失败须在本交付内修复；若需要改变产品或架构契约，返回讨论，不以文档限制替代必做保证。

必须完成针对边界和持久恢复的自动回归、Rust 检查/构建及相关测试、前端 typecheck/lint/build、统一入口状态测试，并在同一签名构建上以短测试时段完成真实双路定时启停、手动覆盖、应用重启和至少一次睡眠/唤醒验收。模拟时钟测试不能替代原生生命周期检查。更新架构和操作说明，完成需求/异常路径/最终架构审查后，才可标记原子交付完成；本 PRD 不自动授权安装到正在使用的录音客户端。
