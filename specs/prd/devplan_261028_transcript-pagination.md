# 转录详情分页与连续滚动

修复精转已保存、但因分页未加载而被粗转替代的展示错误；详情滚动接近底部自动加载下一页，移除“显示更多文字”。用户要求基于最新代码修复并提交 PR。

## 执行台账

### 开发契约
- 必赢场景：精转第 100 句之后不会误显示尚未核对精转覆盖的粗转；下滑自动显示后续精转，保留真正未覆盖的粗转。
- 原子交付：一个前端修复批次，包含回归、文档、审查及 PR；复用既有 IPC，无持久数据迁移。
- 必须保证：混合内容按已知时间范围展示；粗转单独查看、全精转、只有粗转、双音源和长记录定位保持可用；滚动加载同一时间只发起一批，失败保留正文且可重试，关闭淘汰迟到响应，后台刷新不重置阅读位置。
- 明确不做：改动识别/计费策略、重转用户音频、安装或重启客户端、改造 Core 分页协议。
- 本次负责的问题：分页结果被当成完整覆盖；滚动触发、请求竞态及空页/失败处理。
- 状态来源与生命周期：Core 是转录事实来源；DetailDrawer 持有已加载页与当前请求序号；分页是否还有结果是本次响应的事实，不能由事件处理状态或累计条数猜测。
- 复用抽象：DetailDrawer.load/detailRequest/initialScroll、detail-entry.pageCoversTime、既有粗转覆盖判定、TabPanel、LoadError。
- 新增机制：仅现有详情组件内的请求进行中/分页失败 UI 状态及 IntersectionObserver；纯函数提取展示投影用于回归。无新 owner、store、协议或自动失败重试器。
- 架构约束：GUI 只经既有 IPC 读取；原文/音频/时间轴不改，云处理状态和客户端加载状态分开。

### 验收与结束条件
- 合成密集精转/稀疏粗转夹具复现原 bug，验证 100 条边界、真正缺口、两路来源和最后一页。
- React 交互验证自动加载、重复观察去重、刷新已读页以反映识别更新、失败手动重试、切换页签/粗转视图、关闭和刷新竞态。
- 浏览器实际滚动检查列表连续加载、阅读位置及长记录定位；使用合成内容，不访问真实业务数据。
- 静态、前端构建、Node 回归及仓库全量离线门禁；代码改变重跑受影响检查，文档状态不影响代码检查。
- requirements/adversarial 独立审查并修复阻塞后，最终 architecture PASS；提交并创建 PR。无本次 OS 集成变更，安装版验收不属于 PR 范围。
