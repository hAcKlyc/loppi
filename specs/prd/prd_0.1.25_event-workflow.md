# 智能标签与事件自动流程

## 执行须知（给空 session 的你）

先读 [CONTRIBUTING](../../CONTRIBUTING.md)、[整体架构](../ARCHITECTURE.md)、[核心处理算法](../tech_docs/algorithms.md)、[Agent Context](../tech_docs/agent-context.md) 和 [Agent CLI 指南](../../resources/agent/loppi-context/references/cli.md)。第 4 节列出当前代码入口，按符号名定位，便于在代码移动后继续核对。研究报告只提供产品背景，交付契约以本文为准。

本文是一项原子交付。开发批次只用于实现、验证、审查和提交。GUI、CLI、协议、旧数据迁移、隐私契约和第 7 节的验收门槛须一起完成后统一上线。若现有事件身份或任务机制无法承载第 4 节的边界，先验证具体缺口，再提交设计决策。

## 1. 目标与必赢场景

loppi 已经用 LLM 把粗转录整理成可回看的事件。用户希望把「工作会议」这类判断变成可配置、可纠正的标签。「这是一个很重要的信号，因为我的目的是需要基于这个标签，来对后续的动作做决策。」同一个标签可以供多个处理规则使用。用户希望在设置里看得懂规则，在事件里看得见动作和结果，也能让 Agent 用 CLI 对特定事件做同样的事。

**必赢场景。** 用户定义「工作会议」及判断标准，以「其他」兜底。设置仅工作会议自动精转，再创建读取精转稿的「会议纪要」策略。会议自然稳定或被用户确认结束后，loppi 按标签安排精转，稿件就绪后生成纪要。在同一事件的「会议纪要」标签页查看结果，用 `+` 手动生成「行动清单」，并在同名标签页查看。如果会议被误标为「其他」，用户改标签时会看到要补跑什么，点击「保存并处理」即可补上缺少的步骤，已有精转稿直接复用。Agent 能发现同一个事件和策略，按明确授权运行，跟踪任务并读到同一份结果。

**交付范围。** 一套智能标签、可配置的自动精转和 LLM 策略、配置依赖检查、事件确认与人工纠标、自动及手动执行、结果版本与桌面展示、Agent CLI 及发现文档。

**范围边界。** 多套标签、任意流程图或策略串联、布尔规则表达式、全库重打标签和批量回填、前端切换历史版本、外部投递及 MCP 写工具均在本文交付范围之外。

## 2. 产品行为与数据契约

### 2.1 智能标签

- 一套标签整体设置为单选或多选。每个自定义标签有名称、判断标准和稳定 ID。「其他」为内置兜底，固定放在最后。单选取最符合的一个，多选取所有符合标准的标签。「其他」仅在判断有效且没有具体标签命中时使用，和具体标签互斥。
- 复用整理粗转录的现有 LLM 调用，将当前标注模式、可选标签及判定标准放入受控系统指令，要求模型在同一次事件输出中返回选中标签。事件范围、摘要、主题和标签各自校验。模型猜测的标签、缺字段、非法组合属于打标失败，独立保留有效事件与摘要。正在续接的事件可展示暂定标签，自动判断读取确定时的标签。
- 自动结果可由用户在事件详情纠正。人工标签优先于后到的模型输出。名称可编辑，规则继续引用原 ID。停用或删除标签前列出当前依赖它的精转及策略规则，需一并处理后保存。历史引用保留可辨认名称；人工修改旧事件时按当前模式校验。
- 打标失败和旧事件「尚未打标」各有状态。打标失败可重试该事件的打标或人工补标。按标签触发的动作在有有效标签后再判断。自动精转采用「全部有效事件」时，标签失败仍可按事件本身判断精转。分类结果及失败状态均与原声和粗转保留规则分离。

### 2.2 自动精转与生成策略

| 配置 | 字段 | 行为 |
| --- | --- | --- |
| 自动精转 | 全部有效事件 / 包含指定标签 | 默认全部有效事件，承接现行行为。标签模式须至少选一个，任一命中即可安排。原有显式手动精转入口继续提供。 |
| 自定义策略 | 名称、Prompt、输入来源、触发标签 | 输入为「粗转录」或「精转录」。触发标签为空时仅手动运行；选多个时任一命中。不同策略可独立运行，同一事件因多标签命中同一策略时只安排一次。 |

依赖精转稿且有自动触发标签的策略，所有触发标签必须被自动精转覆盖。按标签精转时，缺少项等于「策略触发标签减去精转标签」。保存策略时列出缺项，用户点「加入并保存」后，把缺项并入精转列表并一起保存。切换精转模式、移除标签或修改标签定义时，反向检查并显示受影响的策略和标签。有效配置以一次原子保存生效。仅手动策略由用户单次选择输入，适用手动执行契约。

### 2.3 先确定事件，再判断规则

| 事件状态 | Core 行为 | 用户可用的处理动作 |
| --- | --- | --- |
| 进行中 / 等待稳定 | 持续整理和续接，保留当前范围与暂定标签 | 「确认事件结束」，确认范围，必要时等待现有事件整理完成 |
| 已确定，正在判断规则 | 依据确定的范围和标签作一次初始判断，记录已安排、跳过或待标签的动作 | 查看判断状态 |
| 自动规则已判断 | 精转和生成按已安排的依赖在后台推进 | 「执行策略」及生成区 `+` 开放，按所选策略的输入状态决定何时执行 |

自然稳定与人工确认汇入同一规则判断。判断结束包含「未命中」和「因标签失败暂缓」，与后台任务全部成功是两个状态。确认结束锁定的是事件时间范围，后续录音继续采集。已结束的普通「未整理素材」可从原卡片选定范围并确认为事件，完成必要的整理后进入同一流程。显式手动精转形成的固定范围继续作为可处理的未命名事件，可手动执行策略和复用已有稿件。其显式精转沿用原请求；需要加入事件打标与自动流程时，可将所选范围确认为事件。

全局设置保存后应用于后续进入流程的事件。已有事件的任务按已接受的配置执行。处理历史事件通过明确的单事件操作。事件仍未稳定时，纠正标签只保存人工标签，等待确定后统一判断。

对已确定事件改标签，保存前由 Core 预览待补的精转或策略、将撤掉的未提交动作，以及哪些步骤复用现有稿件或任务。用户点「保存并处理」后重新核对预览并提交。未提交且失去触发条件的动作撤销；已提交的允许完成，已有结果保留。精转如还被其他有效任务或手动请求使用，保留该共享任务。已有成功版本与该事件当前有效输入匹配时可满足已执行动作；显式重新执行可生成新版本。

### 2.4 手动执行、输入与结果

- 事件确定且完成自动规则判断后，用户可以手动选任一已配置策略。触发标签用于自动选择；手动选择本身就是对该事件执行指定策略的明确指令。能按配置取得文字时直接运行。
- 手动选了精转策略且当前无可用精转稿时，展示两个按钮。「直接执行」使用当前可用粗转稿，明确显示输入来源。「先精转，再执行」复用已有适用的精转任务，必要时为该事件安排缺失的精转，精转稿就绪后继续生成。按钮依据实际素材可用性启用，并提示缺少的内容。选择只作用于这一次运行。
- 自动策略始终按已配置的粗转或精转输入执行。精转正在排队或部分完成且仍可补齐时等待；精转失败、无可识别文字、无可补转的原声时，显示具体阻塞或失败。人工补齐可接续原等待动作。精转稿的可用性使用 Core 现有范围、来源、覆盖和文字判定，不能把一个物理子任务的成功当成整场就绪。若处理已覆盖全部可用输入但存在已知录音缺口，结果携带范围与缺口提示。
- 每次成功执行在「事件 × 策略」下追加一个版本，记录实际输入类型、输入范围/版本、策略执行快照、生成时间和正文。前端展示最新成功版本。新执行的排队、失败、取消独立显示，已有成功正文可继续读取。自动与手动结果落在同一个版本序列。
- 策略使用转录正文和理解所需的最小事件时间、来源与说话人信息。精转采用当前可见、含人工纠正的精转文字；粗转使用当前有效粗转。结果标明是生成内容，转录与事件的通用摘要仍作为独立内容读取。

## 3. 面向用户的前端交互

### 3.1 智能识别

在「智能识别」下提供「处理队列」「智能标签」「自动流程」三个标签页，默认进入处理队列。智能标签与自动流程共用配置草稿和保存操作，切换标签页保留改动。通用设置中的本地组件与云服务配置仍沿用原入口。

- **智能标签。** 顶部选择单选或多选，下方在标签库中按名称和判断标准查看，单条新增或编辑在弹窗中处理。「其他」在末尾显示固定兜底说明。删除或停用有引用的标签时，在当前操作内列出受影响规则，保存前给出可处理的依赖。切换模式时说明对后续标注生效。
- **自动流程。** 先设自动精转模式和触发标签，再列出自定义策略。列表展示各策略的输入类型和触发标签，单条编辑包含名称、生成指令、输入类型和触发标签。留空时显示「仅手动」。对依赖缺口显示具体策略和标签，「加入并保存」完成一次确认。反向修改精转时定位受影响策略。
- 设置说明要让用户知道哪些转录文字会发送给现有 LLM，以及哪些设置会扩大自动精转的音频范围。执行计划和预览来自 Core，前端只负责表单、展示及收集确认。

### 3.2 时间线与事件详情

- 时间线事件可见标签与打标失败提示。详情头部第一行显示时间范围、可点击标签和状态，第二行显示标题，点击标题可原地编辑。改名保留范围与声源，并沿用事件修订校验。编辑弹窗沿用单选或多选规则，按预览分别显示「将补跑」「将撤掉」「复用现有精转」。若计划已变化，刷新预览后让用户确认当前计划。
- 未确定事件的处理入口使用「确认事件结束」。沿用确认起止时间的交互，确认后显示整理及规则判断进度。历史未整理卡片先选起止时间及适用声源，确认成事件后打开该事件。录音播放、日期导航和现场记录仍使用现有组件。
- 左侧播放器下方的标签行使用 **文本转录　音频信息　会议纪要　…　＋**，每个已执行策略按名称显示独立标签页。沿用现有下划线选中态，标签过多时横向滚动。`+` 位于这些标签之后，键盘可聚焦且有「执行策略」无障碍名称。右上角「··· → 执行策略」和 `+` 打开同一个选择器，列出全部已配置策略及输入来源。
- 手动提交成功后自动切到该策略的标签页。尚无正文时展示排队、等待精转、生成中、失败及可用重试。已有成功正文时，标签页直接展示 Markdown，输入与运行信息可通过 CLI 读取，后续失败仍可重试。正文独立适配 H1–H6、段落、列表、引用、代码和表格。自动结果完成时更新对应策略标签，尊重当前选中项。
- 详情首次加载只读取标签、阶段、策略结果元数据和状态；生成正文随选中结果有界读取。生成的长正文使用左栏现有独立滚动区。未执行过策略的事件通过 `+` 打开策略清单；清单为空时提供设置入口。失败提示具体到输入缺失、精转或 LLM，避免用户误判已生成。

## 4. 技术架构与职责

### 4.1 当前事实与延续方式

| 当前实现 | 本次延续方式 |
| --- | --- |
| `events::FIT_SYSTEM` 和 `publish_fit_with_input` 负责粗转候选及主动重整的事件发布；`events::rebuild` 支持固定范围重建 | 在已有整理输出里增加独立的结构化标签。固定范围重试、补标沿用相同标签契约和已有 LLM 执行基础设施。 |
| `events::asr::settling_state` 和 `refresh` 给自然稳定及精转规划提供信号；`events::event_state` 将待规划 ASR 投影成「等待事件稳定」 | 把事件确定与规则判断放在 Core 的事件域。复用现有观察信号，事件阶段由事件判断产生，ASR 状态独立反映识别进度。 |
| `events::completion::finish` 当前直接安排精转；`create_event_in` 及手工调整路径也有隐式精转分支 | 确定、建事件和范围变化走同一规则判断。只在用户明确要求精转时走现有直达 ASR 路径。保留 ASR 的有效引用、覆盖扣减及范围校验。 |
| Core 的 `take_task_fair`、云 worker 循环、现有 LLM/ASR 暂停、准入、凭据、重试及用量统计 | 新增明确的生成任务用途，继续使用现有 LLM 队列。粗转、精转和生成各自消费原有输入。识别与生成在 Core 中有独立的结果发布校验。 |
| Core 为唯一状态写入者，GUI 经 Tauri IPC，CLI 经同一本机协议 | 界面和 CLI 共用配置校验、计划预览、确认、入队和读投影。无需另建前端流程状态库、Agent 服务或第三条执行队列。 |

核心代码定位见 [事件核心](../../crates/loppi-core/src/events.rs)、[精转规划](../../crates/loppi-core/src/events/asr.rs)、[确认结束](../../crates/loppi-core/src/events/completion.rs)、[事件重整](../../crates/loppi-core/src/events/reorganization.rs) 和 [Core 请求与云任务分发](../../crates/loppi-core/src/main.rs)。

### 4.2 权威状态与生命周期

- **配置。** Core 在 SQLite 内持有当前一份配置和修订号，包含标签定义/模式、精转规则、策略。分类请求使用当次标签定义快照，自动判断前验证标签仍适用。若期间标签标准或模式已变化，使用已有固定范围 LLM 路径补齐分类或显示失败；单纯修改策略或精转规则可直接使用有效标签。策略任务只保存执行所需的配置快照和引用，避免每个事件复制全部设置。
- **事件。** 继续以 `named_events` 和具有独立身份的 `manual_ranges` 识别对象；普通素材确认后才有归属。自然确定复用现有等待区间、同源后续事件及积压信号，手动确认复用已确认范围。事件可确定且标签失败，不会使事件永久卡在进行中。首次判断及入队结果按事件当前确定范围记录，支持重启恢复。已提交到该阶段的自动决定与全局配置编辑解耦。人工纠标、针对单个事件重新判断或重新确认范围时，按当前设置预览并执行受影响的动作。
- **触发。** 规则判断是 Core 中可重复计算的有限判断。输入为事件身份、范围、标签及设置，输出为自动精转与匹配策略，连同跳过/待输入原因。自动动作按事件当前确定范围和策略身份去重。重试、启动恢复及重复发布复用原有动作；多个策略可引用同一精转覆盖。带明确输入的手动执行只授权该事件该策略的动作；在途同等输入复用，已有成功结果可由用户显式生成新版本。
- **任务与结果。** 生成复用现有任务的持久身份和恢复机制；等待精转为生成动作的输入依赖，不占 LLM 执行槽。按事件身份、确定范围、来源、策略快照及实际输入版本绑定，发布时再次校验。输入版本以有效转录的稳定标识及内容修订或摘要哈希核对，复用 Core 现有转录库。新持久状态限配置、事件标签及判断/等待依赖、生成任务关联和不可变成功结果版本。列表和详情的阶段、计数及最新结果由权威状态投影。
- **变更与失败。** 配置应用、人工标签保存与待办调整、确认成事件与可确定的安排，各自以 Core 事务提交。预览根据当前对象和动作状态生成可校验标识，保存时重算；若动作差异、事件或配置修订已改变，返回新的预览。使用现有请求 UUID 与持久回执。已派发任务仍需校验当前素材与事件身份；清理、删除或范围失效后的迟到结果无法发布为当前内容。已成功的旧范围版本可保留其归属和范围标识，受清理范围约束。以新的确定范围为输入执行时复用适用的精转覆盖。
- **提交不明。** 客户端收到超时或断开时，用同一请求 UUID 和相同参数取回已提交回执。不同参数复用 UUID 返回冲突。供应商侧的确认不明走现有 provider 重试、退避与用量语义。应用保证同一动作的入队和成功版本发布幂等，供应商计费和网络投递遵循现有队列契约。

### 4.3 数据边界、迁移与安全

- 生成继续使用现有 LLM 凭据、模型、队列准入、外发保护、取消和用量记录。模型的系统指令由固定输出契约和用户策略 Prompt 组成。转录与事件元数据进入材料区；仅解析固定 JSON 正文项，正文支持 Markdown。模型输出只成为结果数据。GUI 使用既有安全 Markdown 渲染方式，禁用原始 HTML 与自动远程资源加载。
- 生成输入以确定后的时间范围和声源为边界，复用 Core 的可见转录与纠错语义。按现有固定范围重建的量级设置序列化输入上限（512 KiB），同时遵守当前模型和协议的更小实际限制。超限明确报错，保证结果所标示的范围可核对。限制配置体积，使设置提交和读取低于现有 IPC 帧上限；测试中文、换行和 JSON 转义后的大小。长正文按稳定结果版本分页。
- 清除全部数据按实际输入范围与音源同步清除相交的结果版本、使相关等待和在途生成失效。删除事件后，其策略结果和任务对 GUI、CLI 不可用。清除原声遵循现行文字保留规则，保留文字派生的结果，未发出的原声请求仍受清理屏障约束。已外发内容遵循既有供应商边界。更新 `PRIVACY.md`，明确配置精转策略后，精转稿及最小上下文可发给 LLM。Prompt、转录、生成正文和凭据进入现有数据保护边界，诊断与任务错误只保留必要标识和脱敏原因。
- 使用增量 SQLite 迁移，保留既有事件、人工范围、转录与 ASR 请求。老事件可显示「尚未打标」并按需单独处理。升级和保存规则时保留已接受的任务，不对旧库补打标签或批量生成。升级前已进入原精转链路的事件继续消化已有待办；升级后进入新流程的事件适用新配置。新 CLI 与 Core 使用相同内部协议版本和安装包，协议不匹配时明确报告并指导使用配套 CLI。保留既有命令和 `loppi.context.v1` 的既有字段契约。
- 当确认历史素材时，Core 用现有范围、声源、所有权和同源非重叠约束，创建或确认用户选中的有界事件。复用现有人工建事件和固定范围 LLM 整理；用户确认的起止时间和声源是结果归属边界，模型只补充内容、标题和标签。重复提交复用同一事件回执，并发范围冲突要求重新读取。现有手动精转范围按其稳定身份处理和复用稿件；标题状态与事件是否可处理分开。

## 5. 面向 Agent 的 CLI

### 5.1 命令和职责

沿用现有 `loppi event` 管理事件，新增 `loppi workflow` 管理配置、策略执行和结果。事件发现优先用现有只读 `context list` 与 `context event`。命令中的 ID 取 Core 返回的稳定值，`REV` 指对应对象的修订，所有管理命令的毫秒范围为 Unix 毫秒、左闭右开。手动执行和结果命令可用命名事件 ID 或独立手动范围 ID，返回明确的对象类型。未命名事件由现有时间线或范围详情发现，采用它返回的范围修订。

| 命令 | 返回与写入边界 |
| --- | --- |
| `loppi context list --date today [--tag TAG_ID]` | 只读。按当前有效事件标签 ID 筛选；保留原时间范围、分页和空结果约定。可选标签元数据也供 `context event EVENT_ID --section overview` 和 `event show` 读取，提供事件修订并区分标签、打标失败、旧事件尚未打标、事件是否已确定及自动判断状态。列表和概览只带元数据。 |
| `loppi workflow config show` | 只读。返回带修订号的完整设置文档，包含标签 ID/名称/标准、标注模式、精转设置与策略定义。常规发现优先用下方的 `strategies`。 |
| `loppi workflow config set --file PATH --if-revision REV [--preview] [--add-required-asr-tags]` | 将一个完整设置文档按预期修订应用。文件为 `-` 时从标准输入读，便于提交多行 Prompt。保留已有 ID，新项 ID 由 Core 分配，应用后返回规范化 ID 与新修订。预览只做校验，返回冲突与将补齐的标签。显式 `--add-required-asr-tags` 等价于 GUI 的「加入并保存」。反向检查和修订冲突与 GUI 相同。 |
| `loppi workflow strategies` | 只读。返回当前配置修订及全部可选策略 ID、名称、配置输入和自动触发标签。元数据列表省略 Prompt 正文。 |
| `loppi event complete EVENT_ID REV [--from-ms FROM --to-ms TO]` | 复用现有 `ConfirmEventCompletion`。范围默认采用对应事件修订；提供时起止成对。返回事件或整理任务身份与状态。等待完成后再手动执行策略。 |
| `loppi event confirm-range FROM TO --sources SOURCE [--title TITLE]` | 对单个历史未整理区间按现有来源和范围约束确认成事件。返回可跟踪的事件 ID 以及必要整理状态。结果与 GUI 的「确定成事件」相同。 |
| `loppi event tags EVENT_ID REV --tag TAG_ID … [--apply PLAN]` | 默认只读预览完整标签选择及动作差异，返回计划标识。传回相同标签和计划标识才按「保存并处理」提交。计划变化返回当前预览和冲突原因。打标失败的人工补标使用该入口。 |
| `loppi workflow run EVENT_ID STRATEGY_ID --if-revision REV --config-revision CFG_REV [--input configured\|coarse\|prepare-precise]` | 按已读取的事件和策略配置明确执行一次并返回 run ID。默认 `configured` 使用策略配置；缺精转稿时返回可用选项。显式 `coarse` 对应「直接执行」，`prepare-precise` 对应「先精转，再执行」，用于精转策略的手动选择。响应区分新入队、等待精转和复用已有运行。未确定时提示先确认事件结束。 |
| `loppi workflow runs EVENT_ID [--run RUN_ID] [--strategy STRATEGY_ID] [--cursor CURSOR]` | 只读。按事件读取有界运行元数据，也可查询一次运行。返回触发方式、实际或预期输入、状态、失败原因、相关 LLM/ASR 任务 ID、结果版本 ID 及下一页。已有任务重试沿用 `loppi cloud retry TASK_ID`。 |
| `loppi workflow result EVENT_ID STRATEGY_ID [--version VERSION_ID] [--cursor CURSOR]` | 只读。默认读最新成功结果；指定版本可稳定续读或核对 Agent 之前引用的内容。返回版本 ID、正文分片、输入来源和范围、生成时间、下一页。指定版本失效时返回原因。 |

### 5.2 自动化和机器可读契约

- 新命令及新增事件子命令默认 stdout 只输出一份 JSON。成功返回 `ok`、`request_id` 及相应数据，失败返回固定 `error.code`、可读说明和结构化详情。退出码沿用 Agent Context 的类别，即 0 表示读成功或写已接受，2 参数错误，3 Core 不可用或协议不匹配，4 忙或超时，5 业务前置条件不满足。老命令的输出与退出行为保持原契约。
- 错误详情至少区分 `event_not_determined`、`plan_stale`、`revision_conflict`、`asr_rule_conflict`、`precise_input_unavailable`、`input_unavailable` 和 `idempotency_conflict`。计划冲突含可重新展示的差异，精转输入缺失含可用输入选项，配置冲突含缺项标签及受影响策略 ID。等精转、队列暂停、处理失败、清理失效均可从运行状态判断。入队成功只表示接受，结果成功以版本 ID 和结果读取为准。
- 运行元数据至少含 `run_id`、`event_id`、`event_kind`、`strategy_id`、`trigger`、`input`、`state`、`reason`、`result_version_id`。`trigger` 区分 `automatic` 与 `manual`，`input` 区分 `coarse` 与 `precise`。`state` 表达 `waiting_precise`、`queued`、`running`、`succeeded`、`failed`、`cancelled` 与 `superseded`；暂停和缺稿原因用 `reason` 表达。状态来自现有任务和输入依赖的投影。读取成功正文时同时返回实际输入和时间范围。
- 读操作和预览走 existing-only 本机 IPC。写操作通过现有配套 Core 请求与回执，遵守原有按需生命周期，不能提升录音许可。修改配置、确认事件、补跑、执行可能外发的操作须有当前用户授权。Agent 在不确定写入结果时复用原 `--request-id`、修订和参数核对；直接读取运行或回执后再决定下一步。命令、模型结果和记录材料之间没有执行指令传递。
- 正文分页沿用 Agent Context 的有界读取原则，游标绑定事件、策略、版本及位置。续页始终读取首次选定的版本，即使此时有新版本。清理或丢失返回不可用，分页不会混入另一版正文。读取能力以同用户本机 IPC 权限为边界。
- `loppi readme`、逐级 `--help` 和 Agent CLI 指南同步发布命令、默认值、结构化输出、预览与写入示例；`context schema list` 同步标签筛选。更新随包 Agent Skill 的发现说明，沿用既有版本和安装管理。共享的只读 Context 可以投影新增的可选元数据；MCP 工具清单和只读边界保持原契约。

### 5.3 Agent 使用样例

```sh
loppi context list --date today --tag TAG_ID
loppi context event EVENT_ID --section overview
loppi workflow strategies
loppi workflow run EVENT_ID STRATEGY_ID --if-revision 7 --config-revision 3 --input prepare-precise --request-id REQUEST_UUID
loppi workflow runs EVENT_ID --run RUN_ID
loppi workflow result EVENT_ID STRATEGY_ID --version VERSION_ID
```

示例的 `prepare-precise` 只在用户授权为该事件精转后使用。已确定事件且稿件就绪时可用默认输入。用于核对原话、承诺或数字时，继续通过 `context read` 查转录证据。

## 6. 关键设计决策

| 决策 | 原因 |
| --- | --- |
| 一套用户配置的标签，现有整理调用负责选标签 | 互斥场景和可并存特征使用同一能力，粗转整理一次即可给出信号。受限选项使触发结果能校验。 |
| Core 统一决定动作，设置时校验精转依赖 | 用户能预先看到扩大自动精转范围的变化。确认结束和精转权限各自清楚，自动提交只有一个规则来源。 |
| 先确定事件，再判断自动流程，最后开放手动策略 | 所有结果绑定一个明确的事件。用户在进行中只需决定是否结束，后续动作有统一入口。 |
| 手动与自动共享执行及版本模型 | 两个按钮只改变一次运行的输入，减少调度分支。版本化避免覆盖历史结果，并让 Agent 可追踪它使用的正文。 |
| GUI 与 Agent CLI 共用 Core 的校验和回执 | 预览、入队和数据读取在两处具有相同结果。重复操作、客户端断连和重启都能用同一身份核对。 |

## 7. 验收与发布门槛

| 编号 | 场景 | 必须观察到 |
| --- | --- | --- |
| A1 | 新装或从当前已发布版本升级 | 默认全部有效事件精转。旧事件、原声、转录及在途任务可读可恢复。升级与保存新配置不为历史事件新增批量识别或生成。 |
| A2 | 单选、多选、无匹配和异常模型输出 | 两种模式按配置选标签；「其他」与失败分开。未知 ID、畸形标签、错误数量均不会覆盖有效人工标签或丢弃有效事件。标签失败时全部有效事件模式仍可精转。 |
| A3 | 只为工作会议精转和生成纪要 | 自然稳定和手动确认都按同一配置安排。多标签命中同一策略只跑一次。未命中的有效事件保留常规摘要和转录，可按需手动选策略。粗转生成可与精转并行。 |
| A4 | 策略保存和反向修改自动精转 | GUI 和 CLI 都列出缺项标签及受影响策略。确认补齐后配置原子生效；配置修订冲突或取消不产生部分更新。仅手动策略可以单独保存。 |
| A5 | 正在记录、历史未整理和未命名事件 | 未确定时可确认结束；确定并完成规则判断后开放两处策略入口。历史素材能选择范围并确定成事件。已有独立身份的未命名事件能复用适用的精转稿。并发范围重叠给出可解释的冲突。 |
| A6 | 标签改为或移除工作会议 | 预览后一次保存。复用已有精转，补齐新动作，撤掉失去条件的未提交动作。已提交结果允许按当前数据边界完成，已有成功版本可读。预览到提交之间变化时必须重新确认。 |
| A7 | 手动运行及版本 | 两个入口列同一清单。缺精转稿有两个按钮，结果记录实际输入；已有任务共享。自动精转失败或部分覆盖有正确状态。重复运行保留版本，前端持续显示最新成功正文。CLI 可稳定分页读指定版本。 |
| A8 | 云队列暂停、并发、断连、重启和清理 | 精转与 LLM 遵守各自队列和用量契约。等待精转不占生成执行槽。重复提交回同一回执，单次成功只发布一个版本。清理与范围变更后的迟到回包不能复活数据；共享精转继续服务仍有效的动作。 |
| A9 | Agent 从发现到执行 | 从配套 `readme` 和帮助即可发现命令。真实 CLI 与 GUI 经同一 Core 在隔离库取得一致的预览、状态和正文。只读命令的离线及不兼容表现可判定；未经执行授权的缺稿响应只提供选择。现有 Context/MCP 读取、分页和工具发现通过回归。 |

实现阶段必须验证下列事项。每项通过后将证据写入开发验收记录；失败先修复和复验，若需改变本 PRD 的权威状态、范围、依赖语义或平台责任，交回用户确认。

1. **流程与迁移。** 在升级前版本的数据库副本验证正在处理、已完成、历史未整理及手动精转区间。注入合成的 LLM/ASR 回包覆盖自然稳定、确认结束、迟到、重试、清理与重复提交。通过标准是 A1–A8 均有对应证据，覆盖迁移重开以及 Core 重启后的待办恢复。
2. **云请求契约。** 通过本地可控响应验证标签 schema、生成的 JSON 正文、实际输入来源、空/部分稿、长中文和恶意模型输出。通过标准是发送范围与来源正确，失败可诊断且原有摘要和已成功结果可用。使用真实计费请求的验证另需明确授权，记录验证范围与结果。
3. **真实界面和 CLI。** 在隔离数据上用配套 GUI、Core 和 CLI 完成必赢场景，验证标准与窄窗下两个入口、键盘焦点、长正文和错误反馈；按仓库支持矩阵验证配套版本，区分本机实测与构建覆盖。通过标准是两端操作可交叉读取、流程无额外重复外发，且现有 CLI 发现和只读上下文回归通过。
4. **文档与发布。** 更新受影响的架构、算法、Agent CLI/Skill、隐私与诊断契约。正式版本以实现完成后走仓库发布流程为准，本文文件名使用当前下一版本槽位。代码、迁移、CLI、桌面交互及文档全部通过后才视为交付完成。
