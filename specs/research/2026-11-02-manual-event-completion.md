# 手动确认事件结束：现有链路核实

日期：2026-11-02。范围：当前工作树源码；未修改产品运行代码，未读取真实录音库，未调用云端服务。

## 已核实事实

1. **「等待事件稳定」是精转规划的读取投影，不是独立的会议生命周期。** `events::event_state` 在 `event_asr_state.planned_version` 尚未对应当前范围时返回 `settling_asr`。`asr::refresh` 要等事件末尾 15 分钟，或出现覆盖其音源的后续事件，并确认相关待办不再可推进，才自动规划。不能仅改前端状态宣称事件已完成。
2. **等待原因包含真实的本地/整理积压。** `asr::settling_state` 检查事件开始至 `min(结束+15分钟,下一同源事件开始)` 的 VAD、粗转、候选整理，以及尚未归入候选的尾部粗文字。确认结束可以取代观察等待，但音频尚未封存、尚未归属到该事件的尾部仍需处理。
3. **弹窗结束时间可能早于真实会议结束。** 候选按最长 15 分钟计算窗与约 5 分钟静默成熟条件处理，LLM 再跨窗续接。会议刚结束时，当前卡片不保证已覆盖最后一个计算窗；简单对当前范围立即精转可能漏掉会议尾部。
4. **自动事件可被后续自动整理延长。** `publish_fit_with_input` 对未锁边界的 linked event / previous event 续接；既有 `boundary_locked` 可阻止常规自动边界更新，但代表人工边界事实，不是仅仅提前精转。显式用户重组可以调整人工事件并清除旧锁。是否冻结、冻结哪一个时间，需要产品选择。
5. **「重新精转」不能直接用作确认结束。** `retranscribe_event_in` 删除当前 ASR 引用、创建新运行标识并把纠错转待核对，这是明确的新付费重跑。正常 `asr::schedule` / `plan` 会按现有任务引用扣除覆盖，更适合复用，新增结束操作不应默认重跑成功或在途请求。
6. **摘要没有排在精转后。** 常规摘要与轻量理解由事件整理同一次 LLM 调用，基于粗转增量生成；精转完成不会自动触发重建。`events/rebuild.rs` 已有固定边界、完整粗转的显式重建能力，但会新增一次 LLM 请求。不能把本需求描述为已有的「结束→精转→最终总结」流水线。
7. **更多入口当前是管理弹窗。** `DetailDrawer` 顶部外显导出、清理、编辑；更多进入 `App.openTools` 的拆分/合并/取消标注弹窗。处理状态在音频信息页，重新精转与查看智能识别也在此。要实现收纳需要真正的操作菜单，再从菜单进入各自已有交互。

## 方案上的实际取舍

2026-11-02 用户补充选择：确认弹窗预填当前事件起止时间，两端均可编辑，人工矫正后确认。默认不采用点击时刻，也不要求程序自动推断/续接尾部。

- 按当前显示范围确认：改动集中在提前 ASR 规划与是否锁边界；能立即处理已有范围，但可能不含会议尾部。
- 补齐到点击时刻：更贴合“刚开完会看整场内容”，需要明确本次截止点，让尾部材料归属完成后及时规划；不能把现有全局 force-candidates 简单当作单场结束，也不能擅自吸收期间其它已命名活动。
- 后续自动是否可扩展：这是与截止点独立的产品契约。只想提前查看可保留续接；明确结束则应避免后续自动内容接回。已有人工边界能力可用，是否与本次结束共用需在选择确认后设计。

### 新选择下的复用边界

- `edit_event_in` 已有范围校验、同源事件冲突检查、修订校验、人工边界与精转规划。边界变化时清空摘要与理解，避免继续展示旧范围的概括。
- 但当前普通编辑在时间/来源未变时不规划 ASR，也不锁边界。新增确认动作必须即使用户不改默认值也生效，不能只换一个表单入口。
- “确认结束并开始处理”宜是一次原子提交：范围保存与解除观察等待同时生效，沿现有 Core 事务和正常 ASR 覆盖规划；不串联两次可部分成功的 GUI 请求。
- 未来时间、同源已有事件冲突、原声缺口和跨日日期需清楚呈现；不静默裁剪范围、不自动合并相邻事件。具体处理规则仍作为建议，尚未由用户确认。

## 两分支补充（同日后续讨论）

用户已明确：不改时间直接确认既有事件；修改任一端则重新切割、重新用 LLM 识别。

- 不改时间分支可以保留现有标题、摘要和理解；完成事实需要同时约束后续 linked 更新、previous-event 续接及在途旧结果。仍保留已确认事件的占用范围供正常冲突/投影判断，不能从系统事实中丢弃后导致重复创建。
- 「事件已完成」与精转状态是两个含义；结束观察后仍可能待精转、精转中或失败，不能用同一个完成文案掩盖处理进度。
- 时间有改动时，现有 `reorganization` 在输入里把用户时间当定位参考，并带邻近事件完整材料，允许重划边界和重组其它事件；它发布后 `boundary_locked=0`，但 `queue_asr` 的 manual 参数为 true，已经会立即规划精转。可复用现有重整与精转衔接，但直接接该入口不能承诺人工时间硬边界、只处理本场或后续不再续接。
- 现有 `rebuild` 仅按固定范围重建摘要与理解，不重切事件。需要先决定新人工时间是否必须遵守、是否允许多事件输出，再选择和复用相应发布原语；不应由技术实现静默决定。
- 建议改时间分支：重新识别成功才一次替换旧组织结果，失败保留旧内容供重试；本次完成结果应如何标记为已确认，待用户确定。物理原声、粗转与有效 ASR 引用不因 LLM 重跑而全部失效。

用户已进一步确认：人工修改的时间仍是参考，允许模型重新判断边界；需要在 LLM 输入中明确这些时间是用户手动调整过的。无需新建固定人工边界型重识别；优先复用既有 `reorganization`，补充本次触发来源与目标事件身份，协调其它已确认事件的保护范围。

用户最终确认：本次重新识别成功的新结果也一律视为已确认结束，以后不再自动续接。结束保护与新结果在成功发布事务中共同生效，精转直接规划，不增加再次确认/稳定等待；失败时保留旧结果。此语义仅属于本次「确认事件结束」入口，不能静默改变普通新建/重新整理入口继续允许自动组织的既有契约。需要核实已有边界锁对 linked 更新中的标题、摘要、理解的保护是否充分：目前仅锁边界，不能直接推定能冻结所有识别结果。

## 建议的共同约束（尚非用户决策）

- 顶部常驻处理状态；只有等待稳定时提供清楚的可点击提示，点击进入确认。
- 确认表达“事件已结束”和“精转仍在处理”两个事实，提交受理不显示“精转完成”。
- 原声缺口、队列暂停、网络/凭据问题沿既有状态呈现；不因人工确认绕过暂停，也不把失败当完成。
- 保留已完成与在途精转，只补实际缺口；重复确认复用既有修订与请求回执。
- 提交期间事件范围已变化，刷新最新范围再确认，不能静默应用旧弹窗的结束意图。
- 更多菜单收纳事件级管理操作；播放、时间轴、正文和现场记录的核心交互是否属于“外显功能”需在 UI 范围中回放确认。
