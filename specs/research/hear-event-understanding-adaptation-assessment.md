# 事件理解输出的软件适配评估

基于当前工作区 HEAD `18cba03` 的代码阅读，以及[第 4 版真实样例](2026-10-23-event-json-example/README.md)。本次是影响评估，没有修改产品代码、运行付费模型或提交开发 PRD。工作区已有的界面修改未动。

2026-10-24 用户已明确范围：沿用窗口分析，传入上一轮摘要和结构化结果；数据层不限制摘要字数，界面按行省略；新增字段本次只做存储与处理链路，新的前端展示属于后续需求。本文按这一决定调整，早先独立事件任务和详情展示建议不再作为本次要求。

## 1. 结论

当前范围是一项集中在 Core 的窗口理解增强：完善摘要写法，移除摘要业务字数硬限制，持久化并在下一轮回传 `topics`、`key_points`、`mentioned_objects`。原有卡片行数省略继续复用，不增加详情展示。相比首次评估，省去了独立任务调度与新界面的范围。

主要复杂度来自三个问题：长事件如何持续形成完整结果；原文引用怎样跨请求保持有效；记录被修正、裁剪或删除时派生内容怎样一起更新。采集、VAD 和粗转模型本身没有因这三个输出字段而改变的必要。

## 2. 当前代码实际支持到哪里

| 环节 | 当前事实 | 对接入的影响 |
|---|---|---|
| LLM 请求 | `cloud.rs::chat_content` 已请求 JSON 对象，非严格字段级 schema | 沿用现有 provider；保留类型与引用校验，不以摘要字数清空结果 |
| 摘要 | `events.rs::FIT_SYSTEM` 仍要求最多 240 字符；`fit_summary` 超限返回 None | 360 字符样例现在会失去摘要，不能只改 prompt |
| 新字段发布 | `publish_fit_with_input` 逐项读取当前字段，没有读取 `understanding` | 新字段即使由模型返回，也不会保存或展示 |
| 跨窗上下文 | `fit_context` 提供旧事件标题、摘要、版本及有限尾部文本 | 不足以直接复现样例对整场全部文本的分析 |
| 数据与协议 | `named_events` 有 summary；Rust/TS 的 `TimelineItem` 只有 summary，无三个扩展项 | 本次先做内部迁移、发布和上下文读取；无需因尚无前端消费端而强制扩展 TS 展示模型 |
| 列表与详情 | `cardExcerpt` 优先使用摘要，卡片两行截断；详情目前没有完整摘要/要点的独立展示区 | 按用户范围沿用行数省略；详情新增展示留待后续 |
| 来源定位 | 粗转已有稳定 ID，详情已有按时间定位与回听；输入 observations 未传稳定 ID | 可复用时间导航，但不能直接将样例数组下标当长期引用 |
| 搜索与导出 | 搜索索引类型为 coarse/precise/note/ocr；归档 events.jsonl 当前连 summary 都未输出 | 新数据不会自动获得搜索或导出能力 |

当前代码相较最初生成样例时已有变化：生产 FIT_SYSTEM 已不要求 `unorganized`，发布逻辑也改为逐事件容错；样例仍保留当时的输出基线。后续 PRD 应以当前代码为准，不能直接照搬旧样例中的校验规则或字段说明。

## 3. 必须适配的输出契约

- `summary`：prompt 以具体对象、指标与案例帮助认出事件，此前约 500 字仅作为简洁生成建议；取消本地因超过 240/500 字符而截断或返回 None 的行为。仍允许无可靠内容时为空，界面仅做视觉省略。
- `topics`：开放短文本列表，明确去重规则，空列表是合法输出；不强制从固定主题树选择。
- `key_points`：条目包含完整表述与来源，保留观点归属和未完成状态；模型负责提炼与去重，应用不因展示预算而截短保存内容。
- `mentioned_objects`：类型、名称、语境与来源。对象被提及不等于参与者或已知人物；`entity_id` 不能任模型生成真实数据库关联。
- 缺失与空结果区分：尚未分析、分析失败、分析后没有关键点，不应都被伪装成同一种空数组。可复用任务状态并附分析版本，不一定新增用户可见状态机。
- 延续当前容错原则：某个可选分析条目不合法，不应把有效事件范围、原文或其他事件一起丢弃。坏引用不能显示成有效出处；可以舍弃相应条目并记录原因。

本次不增加面向界面展示的存储截断门槛。类型、引用有效性、输入版本等校验仍然需要；它们与文字长度限制不是同一件事。

## 4. 最大的处理差异：样例是整场，线上是窗口

当前新候选最长约 15 分钟，旧候选可能沿用历史边界；一场长讨论会由多个窗口续接。样例则直接读取 52 分钟范围内的全部粗文本。不能把样例质量直接当作只修改窗口 prompt 后的效果。

先前评估过两种方式，用户已选择第一种：

| 方式 | 如何工作 | 主要代价 |
|---|---|---|
| 扩展现有窗口拟合 | 将前序 understanding 与有效来源带入 context，让模型生成新的事件级结果；保留、合并和去重旧内容 | 上下文与来源映射复杂；压缩累积可能丢细节，旧事件缺失理解或有修正时仍需补读原文 |
| 事件级理解任务 | 事件范围形成或更新后，按当前事件快照读取完整文本，生成摘要及三类信息 | 多一次分析环节，需要去抖、输入大小管理、失败状态和成本控制；长事件不能无限重发全文 |

本次采用窗口累计，不增加事件级理解任务。继续由现有拟合输入、发布、事务和版本机制持有结果，利用已有队列与用量链路。

这里必须明确：

1. previous_events 和 linked_events 中带回有效的上一轮 summary 与 understanding，不能只带旧摘要。
2. 输出语义为更新后的事件级结果：保留仍有效的旧信息，合并重复主题/对象/要点，有明确新证据时修订；不能机械拼接数组。
3. 旧结果和当前观察的来源引用必须明确区分，并能转换成稳定的持久引用。
4. 缺少旧分析或旧分析已失效时，不能把本窗口内容伪装成此前全部活动的理解；具体缺失语义需在输出契约中落实。
5. 长期累计不等于无限追加；模型需要持续整理内容。若输入超出可处理范围，应明确失败或缺失状态，不静默截掉上下文后声称完整更新，也不因此裁掉已保存数据。
6. 迁移不自动重跑全部历史。当前交付不因字段增加而隐式引入全量补算或新的付费流程。

## 5. 模型引用与应用引用应分开

样例的 `evidence_indices: [19,20,21]` 只在那一份输入中有意义。下一个窗口、迟到的粗转、重新排序或重试都可能改变下标。

建议模型仍可输出短引用，但 Core 在发布前使用本次冻结的输入映射，转换为可持久定位的片段 ID、音源、范围及输入版本。当前 `Evidence` 内部已经有 ID，`llm_input` 序列化时没有传出；可以在这一步保留映射或提供短稳定引用，不要求模型猜 ID。

校验需要覆盖：引用确实来自本次允许材料；与对应事件范围和音源相符；支持文字结论的来源有可用文本；引用对象没有在请求期间被删除或改写。前序已有要点的出处也必须能够被保留，不能拿旧窗口下标到新窗口解释。

本次把可定位的出处存好，不实现新的点击要点或回听入口。以后展示时可复用已有时间定位能力，并区分粗转证据与精转段落；这不是当前交付需要新增的前端功能。

## 6. 存储、发布与失效

结果仍由 Core 唯一持有。摘要继续使用已有权威位置，三个列表作为可空结构化载荷，由既有事件拟合发布链路写入并回传；具体列/表安排属于既有数据库内的实现选择。没有必要仅为提及对象先建立全局实体图谱。

保存结果还要记录其输入指纹或版本。关联范围、音源、实际文本与人工修正变化时，旧结果需要失效或明确标为旧结果。发布前核对输入是否仍然有效，防止慢请求把已删除的内容重新写回来。

现有 `summary_for_scope`、`invalidate_summaries`、边界编辑和清理已有相关保护，新增三个列表应加入同一生命周期：

- 改时间范围、改音源、合并或拆分事件：重新确定覆盖范围，不直接沿用不匹配结果。
- 人工修正转录：不能继续显示矛盾的旧要点。若仍只使用粗转输入，可先失效并保留无结果状态；若承诺自动恢复，则重算输入必须能够尊重修正，而非反复用旧粗转生成。
- 仅自然精转完成：不必自动认定粗转派生产物被核验或成为精转结果；是否因此重算属于产品选择。
- 删除相关文本/所有数据：删除或失效受影响的派生文本、索引及导出暂存，不能只删原文。
- 仅清理原始音频、保留文字：按现有清理语义保留文字派生内容，回听入口相应降级。

这些是派生内容的正确性要求，不能把重新核对旧输出变成用户每天必须清空的任务。

## 7. 接口和界面

本次保留现有摘要接口与卡片，原有两行省略已符合「超过几行剩下…」的方向；确认省略只发生在展示层，传输与数据库仍保留完整文本。

三个新增字段的内部类型、发布与上下文读取必须贯通，但无需为未来展示提前改造详情页或增加交互。是否把它们顺带暴露到既有只读协议，按实际链路需要决定，不能反向扩张本次为前端展示需求。

验收应证明新数据确实被存下、下一轮确实读到；不能只检查模型响应里出现了字段，也不能因为本次没有新 UI 就省略持久化验证。

## 8. 搜索、导出与升级策略

如果要承诺「按主题或提及对象找事件」，需扩展现有 FTS/查询投影，并建立 GUI 入口。这不是保存 topics 后自动获得的能力；可作为独立范围选择，不能在未实现时把静态标签做成看似可点击的筛选器。

现有归档导出没有输出 summary。若本次要让用户带走完整事件理解，应显式扩展事件归档、版本说明与引用；按时间或音源导出局部资料时，不能无条件附上含范围外信息的整场摘要/要点。可只导出完全落在范围内的结果，或者明确选择整场导出，不擅自扩大用户选择。

旧数据允许没有新字段，数据库迁移本身不触发付费计算。需要决定新事件是否自动分析、历史事件如何补算，以及失败后如何重试。当前 FIT_POLICY_VERSION 参与候选输入哈希，不能把版本号升级误当成没有费用影响的字段改名。

## 9. 实施前需要收敛、实施后需要验证的内容

已收敛：窗口累计、既有分析触发、上一轮结果回传、数据层不按摘要字数截断、新展示另做。后续落文需核实引用映射、缺失/失效结果处理与迁移；搜索和导出新能力不因字段增加自动加入，若要增加需另行明确用途。

验证应围绕真实失败点：

- 超过 500 字符的合法摘要仍完整保存，前端只按行省略；空结果、坏字段不破坏有效事件。
- 长事件后续窗口不会覆盖掉前面的重要信息，重复输入不会无限追加相同要点。
- 引用不受下标变化、转录分页、双音源交错影响。
- 请求返回前事件被修改或删除，旧响应不能重新发布。
- 人工修正/范围清理后，摘要、要点、对象信息同步失效。
- 结构化字段持久化后能进入下一窗口 context；无新增前端区块，现有列表和播放行为保持可用。
- 若纳入搜索/导出，范围约束与派生数据一致性一起验证。

本轮只做代码阅读与评估，没有执行产品测试；不能据此宣称具体性能、调用费用或开发工期已经验证。
