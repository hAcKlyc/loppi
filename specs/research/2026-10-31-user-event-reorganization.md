# 用户主动发起事件重新整理：技术核实

日期：2026-10-31。源码基线：dev `01772c97c328efa5e303474b47b41f936d06b847`。本报告只核实方案地基，没有修改运行代码、访问真实录音库或调用付费服务。

## 1. 用户已作的选择

- 沿用“新建事件”表单，填写名称、起止时间、声音来源。
- 名称与时间作为本次用户指示，结合已有事件和转录由模型重新组织；代码不按重叠关系直接决定合并或拆分。
- 时间是大致范围，允许模型结合内容调整边界。
- 指示只参与本次；后续自动整理可以重新判断，不新增长期用户规则或锁定。
- 此次可以重组以前手动命名、调整过边界的相关事件；文字纠错、笔记和人物确认保留。
- 架构正确、简单、可依赖；保持链路简单，把LLM当作作决定的人，不增加语义审查、补偿和过度防御机制。

## 2. 当前代码事实

| 入口或符号 | 核实结果 | 对方案的影响 |
|---|---|---|
| `src/App.tsx`：`openForm` / `saveEvent` | 新建默认所选日09:00—10:00、both；保存调用CreateEvent，成功立即提示“事件已保存” | 入口和字段不变；保存语义需要变成任务已受理，不能提前宣称事件完成 |
| `events::create_event_in` | 新建manual事件，标题/边界锁定，拒绝同源时间重叠，立即规划ASR | 不适合承担本次模型重组入口；不能先建一张锁定卡再让模型修补 |
| `events::llm_input` / `fit_context` / `FIT_SYSTEM` | 已有粗转、时间、音源、旧事件摘要/理解及有限前文，同次调用组织事件并更新摘要 | 复用输入/证据准备、同一系统提示及模型调用；增加本次用户指示与完整相关事件上下文 |
| `events::publish_fit_with_input` | 默认自动任务逐事件接纳；按slot关联、续接、过滤冲突；响应遗漏不能删除旧事件 | 需要明确的旧事件修改/退役表达；不能只在prompt里添一句话就宣称支持重组 |
| `events::rebuild` | 只重建一个既有事件的理解/摘要，固定事件边界 | 不能把用户重组伪装成RebuildUnderstanding |
| `cloud_tasks` / `take_task_fair` / `process_cloud_task` | 同一持久LLM队列、手动优先、公平调度、暂停/重试/恢复、一次provider调用，LLM通常180秒期限 | 增加任务目标类型即可；不新增队列、worker、调度器或第二个模型 |
| `Store::mutate_response` / `mutation_receipts` / `core(request, requestId)` | 支持稳定请求ID和事务回执；普通GUI业务mutate目前每次使用新ID | 表单一次提交持有同一ID，不确定结果重查/重发同一命令，避免重复入队；不建设另一套幂等库 |
| `event_asr_refs` / `transcript_tasks` / `asr::inherit` / `asr::schedule` | 事件归属可变，物理ASR输入和远端请求不变；拆合已继承引用并只规划未覆盖原声 | 重组复用同一引用机制；手动精转范围的复用也必须在实现中验证，不把“改分组”当成“重新精转” |
| `split_event_in` / `merge_events_in` / `suppress_old` | 人工工具会退役事件并建立event_suppressions；部分删除入口还会把纠错/人物绑定转待核对 | 不能直接串调这些用户工具执行模型计划，避免永久压制后续自动整理或破坏仍有效的文本绑定；复用下层事务、lineage及ASR原语 |
| `moments` / `knowledge` / `cleanup` | 笔记按绝对时刻归属，纠错与人物以句段/时间为依据，清理有墓碑和在途校验 | 重组只改事件组织；不移动原声/句段/笔记，不删除用户修订；沿原生命周期处理真实跨边界待核对 |
| `QueueView` / `CloudTask` / `taskStatus` | 已有任务状态与失败重试；可按target_kind标记任务用途 | 沿用处理队列显示“用户发起的事件整理”，不新增任务中心或前端状态机 |

## 3. 选定的结构

GUI → `ReorganizeEvents` IPC → Core事务保存一次请求并写入既有LLM任务 → 既有cloud_loop准备上下文并调用FIT_SYSTEM → 共用事件计划执行能力 → 一次事务更新组织结果 → 既有ASR规划/读取。

仅需新增一次性请求载荷和任务用途：建议一个`event_reorganization_requests`表存不可变名称、时间、音源；任务状态继续只在cloud_tasks。完成记录不参与之后自动整理。新target_kind应加入现有cloud_tasks CHECK迁移，保持所有任务ID、输入、ASR引用和用量记录。

模型沿现有events输出提出事件变更，补充对已有event_id的明确修改及显式退役ID；未提及的旧事件保持。Core只做正常schema/时间/音源/对象权限与修订校验，执行事务；不证明语义、覆盖率或会议边界，不增加评审模型。正常自动整理与用户发起共用事件/摘要/理解规范化和落库原语，用户发起仅增加输入意图和相关事件修改权限。

## 4. 需要在开发中证明的事实

- 一次任务能看到跨出用户粗略时间的相关旧事件完整材料，语义重组不被原15分钟计算窗截断。
- 模型明确修改/退役旧事件后，没有旧slot迟到结果复活、永久suppression或新用户锁；新结果可继续进入正常自动整理。
- 同源/双源及双源旧事件的部分音源调整保持来源权限；这属于数据操作边界，不由程序决定语义分组。
- 原ASR任务完成/在途/手动范围均可按实际范围复用；纠错、人物确认和笔记仍有效。跨句边界沿既有待核对规则，不自动重切或付费重跑。
- 普通输入校验、事务、revision和清理检查足以收敛并发；不追加自动重基、额外锁、补偿协议或循环扩窗。
- 扩展FIT_SYSTEM后，自动多窗续接、摘要增量、人工编辑/清理等现有回归继续成立。真实模型需用合成材料验收；当前设计阶段未运行。
